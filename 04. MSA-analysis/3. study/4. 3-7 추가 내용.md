# 1. Kafka Message Key와 Partition

## 1-1. 먼저 Partition을 왜 나눌까요?

Kafka는 하나의 Topic에 메시지를 저장할 수 있지만, 메시지가 많아지면 하나의 처리 단위로는 성능에 한계가 생깁니다.

예를 들어 바로픽에서 하루에 10만 건의 주문이 발생한다고 가정하겠습니다.

모든 주문 이벤트를 하나의 Partition에 저장하면 해당 Partition을 처리하는 Consumer Group의 동시 처리 능력에 한계가 생깁니다.

그래서 Partition을 여러 개로 나눕니다.

<img width="807" height="213" alt="image" src="https://github.com/user-attachments/assets/d8e11fff-707b-4331-9d74-3a8553bf5f27" />


이렇게 분리하면 서로 다른 Partition을 동시에 처리할 수 있습니다.

그런데 여기서 문제가 하나 생깁니다.

같은 주문에 관한 메시지가 서로 다른 Partition으로 분산되면 어떻게 될까요?

## 1-2. Message Key는 왜 필요할까요?

예를 들어 주문번호 1001번에 다음 이벤트가 발생했다고 가정하겠습니다.

```
OrderCreated
     ↓
PaymentCompleted
     ↓
InventoryReserved
     ↓
OrderConfirmed
```

이 이벤트들은 순서가 중요합니다.

그런데 Kafka가 메시지를 무작위로 Partition에 분산한다면 다음처럼 될 수도 있습니다.

<img width="812" height="334" alt="image" src="https://github.com/user-attachments/assets/43b3e434-b089-47ea-b876-732beed41465" />


이 문제를 해결하기 위해 Message Key를 사용합니다.

예를 들어 다음처럼 메시지를 발행합니다.

```
kafkaTemplate.send(
    "order-topic",
    "1001",  // Message Key
    event    // Message Value
);
```

여기서 `1001`이 Message Key입니다.

Kafka는 일반적으로 Key를 해시하여 Partition을 결정합니다.

따라서 같은 Key인 `1001`을 가진 메시지들은 동일한 Partition으로 전달됩니다.

<img width="793" height="286" alt="image" src="https://github.com/user-attachments/assets/5be5b4a3-aeeb-4b77-9ce9-d68d44470200" />


여기서 주의할 점이 있습니다.

같은 Key가 같은 Partition에 배정된다는 것은 Kafka의 일반적인 Key 기반 파티셔닝을 사용하는 경우입니다. Partition 수를 변경하면 매핑이 달라질 수 있고, 서로 다른 Producer에서 발생한 이벤트의 업무 순서까지 자동으로 보장되는 것은 아닙니다.

핵심: Key는 메시지를 어떤 기준으로 같은 Partition에 배치할지 결정하는 데 사용합니다.

## 1-3. Key는 무엇을 기준으로 설정할까요?

| Topic  | 추천 Key                 | 이유              |
| ------ | ---------------------- | --------------- |
| 주문 이벤트 | order_id               | 동일 주문의 이벤트 순서   |
| 결제 이벤트 | payment_id             | 동일 결제의 처리 순서    |
| 재고 이벤트 | sku_id 또는 inventory_id | 동일 재고 대상의 변경 순서 |
| 배송 이벤트 | delivery_id            | 동일 배송의 상태 변경 순서 |

다만 재고는 조금 복잡합니다.

상품 SKU가 같더라도 MFC가 다르면 재고가 독립적으로 관리될 수 있습니다.

따라서 바로픽에서는 `MFC_ID + SKU_ID`를 조합한 Key를 사용하는 것이 적절할 수도 있습니다.

이처럼 Key는 단순히 ID를 넣는 것이 아니라 어떤 데이터의 순서를 보장해야 하는지를 기준으로 결정합니다.

# 2. Consumer Offset과 Commit

이제 Consumer가 메시지를 가져온 다음을 살펴보겠습니다.

## 2-1. Offset이란?

Offset은 Kafka Partition 안에서 각 메시지에 부여되는 순번입니다.

예를 들어 다음과 같습니다.

<img width="806" height="349" alt="image" src="https://github.com/user-attachments/assets/8033d367-4e4d-4c59-aedf-cf3b211ea6ee" />


Consumer는 메시지를 가져와 처리합니다.

그런데 Kafka는 Consumer가 어디까지 메시지를 처리했는지 알아야 합니다.

그래서 Offset을 기록합니다.

## 2-2. Commit이란?

Commit은 Consumer가 처리한 메시지의 위치(다음에 읽을 Offset)를 Kafka에 기록하는 작업입니다.

예를 들어 Consumer가 Offset 0, 1, 2를 처리했다고 가정하겠습니다.

다음에 읽어야 할 메시지는 Offset 3입니다.

따라서 Commit Offset은 3으로 기록합니다.

```
Offset 0  처리 완료
Offset 1  처리 완료
Offset 2  처리 완료
Offset 3  다음 처리 대상
Offset 4  미처리

Committed Offset = 3
```

즉, Offset 3을 Commit했다고 해서 3번 메시지까지 처리했다는 뜻이 아니라, 다음에 읽을 위치가 3이라는 뜻입니다.

이 개념이 상당히 중요합니다.

## 2-3. Commit을 잘못하면 어떤 문제가 생길까요?

여기서 중요한 상황이 발생합니다.

Consumer가 메시지를 처리하는 도중 장애가 발생했다고 가정하겠습니다.

### 상황 A. 메시지 처리 전에 Commit한 경우

```
Offset 0 → 처리 완료
Offset 1 → Commit 완료
Offset 1 → 실제 업무 처리 중 서버 장애
```

Kafka는 Offset 1이 Commit되었으므로 다음에 Offset 2부터 읽도록 합니다.

결과적으로 Offset 1의 업무가 처리되지 않았는데도 다시 읽지 않을 수 있습니다.

메시지 유실 가능성

이를 이해할 때는 At-most-once(최대 한 번) 전달 방식과 연결해서 생각하면 됩니다.

### 상황 B. 메시지 처리 후 Commit한 경우

```
Offset 0 → 처리 완료
Offset 1 → 업무 처리 완료
Offset 1 → Commit 전에 서버 장애
```

서버가 재시작되면 Kafka는 Offset 1을 다시 전달할 수 있습니다.

이미 처리했던 업무가 다시 실행될 수 있습니다.

중복 처리 가능성

이를 At-least-once(최소 한 번) 전달 방식과 연결해서 생각할 수 있습니다.

### 상황 비교

| 구분            | Commit 시점  | 발생 가능한 문제     |
| ------------- | ---------- | ------------- |
| At-most-once  | 업무 처리 전    | 메시지 유실        |
| At-least-once | 업무 처리 후    | 중복 처리         |
| Exactly-once  | 중복 효과까지 제어 | 구현 조건과 범위가 중요 |

실무에서는 메시지를 놓치는 것보다 재처리할 수 있도록 하는 것이 중요한 경우가 많습니다. 그래서 At-least-once를 사용하고 Consumer의 멱등성을 함께 구현하는 방식이 흔합니다.

## 2-4. Auto Commit과 Manual Commit

Kafka Consumer는 Offset을 기록하는 방식도 설정할 수 있습니다.

① Auto Commit

Kafka가 설정된 주기에 따라 Offset을 자동으로 Commit합니다.

```
enable.auto.commit=true
auto.commit.interval.ms=5000
```

예를 들어 5초마다 Offset을 자동으로 Commit하는 식입니다.

장점은 구현이 간단하다는 것이고, 단점은 실제 업무 처리가 끝나기 전에 Offset이 Commit되는 상황을 주의해야 한다는 것입니다.

② Manual Commit

개발자가 직접 업무 처리 완료 시점에 Commit하는 방식입니다.

```
@KafkaListener(topics = "order-topic")
public void consume(
    ConsumerRecord<String, String> record,
    Acknowledgment acknowledgment
) {
    // 1. 메시지 확인
    // 2. 주문 관련 업무 처리
    // 3. DB 저장

    acknowledgment.acknowledge();
}
```

위 코드는 수동 Ack 방식을 사용하는 개념 예시입니다. 실제로는 Spring Kafka의 AckMode와 `enable.auto.commit=false` 등 Listener 설정이 함께 필요합니다.

업무 처리가 성공한 뒤에 Ack를 수행하도록 설계하면 장애 발생 시 메시지 재처리가 가능합니다.

다만 이 경우에도 DB 저장이 성공한 직후 Ack 전에 서버가 죽으면 같은 메시지가 다시 들어올 수 있습니다.

바로 이 문제가 다음에 설명할 멱등성과 연결됩니다.

# 3. 중복 메시지와 멱등성(Idempotency)

이제 실무에서 매우 중요한 문제입니다.

## 3-1. 왜 중복 메시지가 발생할까요?

앞에서 설명한 것처럼 Consumer가 업무 처리를 완료했지만 Offset을 Commit하기 전에 장애가 발생하면 Kafka가 동일한 메시지를 다시 전달할 수 있습니다.

예를 들어 고객이 30,000원짜리 상품을 주문했습니다.

결제 서비스가 다음 이벤트를 받았습니다.

```
{
  "eventId": "evt-001",
  "orderId": 1001,
  "eventType": "PaymentRequested",
  "amount": 30000
}
```

결제 서비스가 결제 처리를 완료했습니다.

그런데 Offset Commit 전에 서버가 종료되었습니다.

서버가 재시작되면 동일한 이벤트가 다시 전달됩니다.

결제 서비스가 별다른 확인 없이 다시 결제한다면 어떻게 될까요?

<img width="830" height="355" alt="image" src="https://github.com/user-attachments/assets/d765aefe-abdf-4427-a41e-3a448854ee02" />


이런 문제를 방지하기 위해 멱등성을 사용합니다.

## 3-2. 멱등성이란?

멱등성은 같은 작업을 여러 번 실행하더라도 최종 결과가 한 번 실행한 것과 동일하도록 만드는 성질입니다.

쉽게 설명하면 다음과 같습니다.

- 동일한 결제 요청이 한 번 들어오면 결제합니다.
- 동일한 결제 요청이 두 번 들어오면 이미 처리한 요청인지 확인합니다.
- 이미 처리했다면 다시 결제하지 않고 기존 처리 결과를 반환합니다.

즉, 중복 메시지가 들어와도 실제 업무가 중복 실행되지 않도록 하는 것입니다.

## 3-3. 실제 구현은 어떻게 할까요?

가장 기본적인 방법은 이벤트 ID를 이용하는 것입니다.

예를 들어 결제 서비스 DB에 다음과 같은 테이블을 만듭니다.

processed_events 테이블

| event_id | status    |
| -------- | --------- |
| evt-001  | COMPLETED |
| evt-002  | COMPLETED |
| evt-003  | COMPLETED |

메시지를 수신하면 다음 순서로 처리합니다.



실제 구현에서는 `event_id`에 UNIQUE 제약 조건을 걸어 중복 기록을 방지하는 것이 중요합니다.

간단한 코드 예시입니다.

```
@Transactional
public void processPayment(PaymentEvent event) {

    // 이미 처리한 이벤트인지 확인
    if (processedEventRepository
            .existsByEventId(event.getEventId())) {
        return;
    }

    // 결제 처리
    paymentService.approve(event);

    // 처리 이력 저장
    processedEventRepository.save(
        new ProcessedEvent(event.getEventId())
    );
}
```

다만 위 코드는 개념을 보여주는 예시입니다. 실제 서비스에서는 `existsByEventId()`와 저장 사이의 동시성 문제를 막기 위해 DB UNIQUE 제약 조건과 충돌 처리를 구현해야 합니다.

또한 결제 PG처럼 외부 시스템을 호출하는 경우에는 DB 트랜잭션만으로 외부 결제까지 원자적으로 묶을 수 없습니다. PG의 멱등성 키와 결제 상태 조회·대사까지 함께 설계해야 합니다.

## 3-4. Kafka의 Exactly-once가 멱등성과 같은 개념인가요?

아닙니다. 이 둘은 구분해야 합니다.

Kafka는 Exactly-once Semantics(EOS)를 지원하는 기능을 제공합니다.

예를 들어 Kafka에서 메시지를 읽고 처리한 다음 다른 Kafka Topic으로 발행하는 작업을 하나의 Kafka 트랜잭션으로 묶을 수 있습니다.

하지만 다음 상황까지 자동으로 해결해 주지는 않습니다.

- Consumer가 외부 결제 PG에 결제를 요청하는 경우
- Consumer가 별도의 MySQL DB에 데이터를 저장하는 경우
- 외부 배송 API를 호출하는 경우

따라서 Kafka 내부의 Exactly-once와 외부 DB 및 API까지 포함한 업무의 Exactly-once는 다른 문제입니다.

실무에서는 중복 메시지가 발생할 수 있다고 가정하고 멱등성을 설계하는 것이 안전합니다.
