좋습니다! 이번에는 Kafka에서 메시지를 처리하다 실패했을 때 어떻게 복구하는지 알아보겠습니다.

Retry Topic, DLT, DLQ는 Kafka Consumer의 장애 대응과 메시지 유실 방지를 이해하는 데 중요한 개념입니다.

먼저 전체 관계부터 잡겠습니다.

- Retry Topic: 처리에 실패한 메시지를 나중에 다시 처리하기 위해 보내는 토픽
- DLT(Dead Letter Topic): 재시도 횟수를 초과하거나 복구할 수 없는 메시지를 보내는 토픽
- DLQ(Dead Letter Queue): 정상 처리할 수 없는 메시지를 격리해 보관하는 논리적 개념

실무에서는 DLT와 DLQ를 비슷한 의미로 사용하기도 합니다. 다만 Kafka에서는 보통 실제 구현된 토픽을 가리킬 때 DLT라는 표현을 많이 사용합니다.

## 1. 먼저 왜 필요한가요?

바로픽의 주문 처리 상황을 예로 들어보겠습니다.

고객이 주문을 완료하면 Kafka에 다음 이벤트가 발행됩니다.

```
{
  "eventId": "evt-1001",
  "eventType": "OrderCreated",
  "orderId": 1001,
  "customerId": 2001,
  "totalAmount": 35000
}
```

이 이벤트를 구독하는 재고 서비스가 주문 상품의 재고를 차감하려고 합니다.

그런데 재고 서비스에서 다음과 같은 문제가 발생했다고 가정하겠습니다.

1. PostgreSQL 연결이 일시적으로 끊김
2. 재고 차감 SQL 실행 실패
3. Consumer가 메시지 처리에 실패

여기서 중요한 문제가 생깁니다.

실패한 메시지를 어떻게 할 것인가?

- 그냥 버리면 메시지가 유실됩니다.
- 무한정 다시 시도하면 다음 메시지 처리까지 막힐 수 있습니다.
- 계속 재시도해도 처리할 수 없는 메시지는 별도로 관리해야 합니다.

이 문제를 해결하기 위한 방법이 Retry Topic과 DLT입니다.

## 2. Retry Topic의 동작 원리

Retry Topic은 실패한 메시지를 원래 Topic에 계속 남겨두고 재시도하는 대신, 별도의 재시도용 Topic으로 전달하는 방식입니다.

<img width="795" height="570" alt="image" src="https://github.com/user-attachments/assets/64169088-136b-43da-8334-f24356c01947" />


예를 들어 재고 서비스가 주문 이벤트를 처리하다 PostgreSQL에 일시적으로 연결하지 못했다고 가정하겠습니다.

| 시도     | 결과               |
| ------ | ---------------- |
| 최초 처리  | PostgreSQL 연결 실패 |
| 1차 재시도 | 연결 실패            |
| 2차 재시도 | 연결 실패            |
| 3차 재시도 | 연결 성공            |

이때 재시도 사이에 대기 시간을 설정할 수 있습니다.

- 1차 재시도: 5초 후
- 2차 재시도: 30초 후
- 3차 재시도: 1분 후

이런 방식으로 재시도 간격을 점점 늘리는 전략을 \*\*Exponential Backoff(지수형 백오프)\*\*라고 합니다.

매번 즉시 재시도하면 장애가 발생한 PostgreSQL에 요청이 계속 몰릴 수 있습니다. 대기 시간을 두면 시스템에 가해지는 부담을 줄이는 데 도움이 됩니다.

### Retry Topic은 왜 원래 Topic과 분리할까요?

여기에는 중요한 이유가 있습니다.

예를 들어 `order-topic`에 다음 메시지가 있다고 가정하겠습니다.

| 순서 | 메시지     | 처리 결과 |
| -- | ------- | ----- |
| 1  | 주문 1001 | 실패    |
| 2  | 주문 1002 | 성공    |
| 3  | 주문 1003 | 성공    |

주문 1001이 계속 실패한다면 어떻게 될까요?

원래 Topic의 Partition 처리를 멈추고 1001만 계속 재시도하는 방식에서는 뒤에 있는 1002, 1003도 처리가 지연될 수 있습니다.

Retry Topic을 사용하면 실패한 1001을 재시도용 Topic으로 넘기고 원래 Topic의 다음 메시지를 처리하도록 구성할 수 있습니다.

다만 여기에는 주의할 점이 있습니다.

Retry Topic은 메시지 처리 순서를 깨뜨릴 수 있습니다.

예를 들어 주문 1001의 재고 차감이 지연되는 동안 주문 1002가 먼저 처리될 수 있습니다.

따라서 순서가 반드시 보장되어야 하는 업무라면 단순히 Retry Topic을 도입해서는 안 됩니다. 주문별 순서 보장 전략, 상태 검증, 멱등성 등을 함께 설계해야 합니다.

## 3. DLT(Dead Letter Topic)는 무엇인가요?

DLT는 재시도 횟수를 초과했거나 재시도로 해결할 수 없는 메시지를 보내는 별도의 Kafka Topic입니다.

예를 들어 주문 1001의 이벤트를 재고 서비스가 3번 재시도했지만 모두 실패했다고 가정하겠습니다.

이제 해당 메시지를 무한정 재시도하지 않고 DLT로 이동시킵니다.

<img width="803" height="443" alt="image" src="https://github.com/user-attachments/assets/87a301cd-f09e-4df1-9d8e-6f45581aa9f9" />


DLT에는 일반적으로 다음과 같은 정보가 함께 관리됩니다.

| 정보           | 설명                   |
| ------------ | -------------------- |
| 원본 메시지       | 최초 전달된 이벤트 데이터       |
| 원본 Topic     | 메시지가 처음 발행된 Topic    |
| 원본 Partition | 원본 메시지가 있던 Partition |
| 원본 Offset    | 원본 메시지의 위치           |
| 예외 정보        | 실패 원인과 예외 메시지        |
| 재시도 횟수       | 몇 번 실패했는지            |
| 실패 시간        | 최종 실패가 발생한 시간        |

이 정보를 이용하면 어떤 메시지가 왜 실패했는지 추적할 수 있습니다.

### DLT에 들어간 메시지는 어떻게 처리하나요?

DLT에 들어갔다고 해서 메시지가 자동으로 해결되는 것은 아닙니다.

운영자는 실패 원인을 확인하고 적절한 복구 절차를 진행해야 합니다.

예를 들어 다음과 같습니다.

| 실패 원인             | 복구 방법                 |
| ----------------- | --------------------- |
| PostgreSQL 일시적 장애 | DB 복구 후 재처리           |
| 잘못된 상품 ID         | 원본 데이터 수정 후 재처리       |
| 필수 필드 누락          | 이벤트 생성 로직 수정 및 데이터 보정 |
| 외부 API 장애         | API 복구 후 재처리          |
| 지원하지 않는 이벤트 형식    | Consumer 코드 수정 후 재처리  |

특히 잘못된 상품 ID처럼 데이터 자체가 잘못된 경우에는 재시도 횟수를 늘려도 해결되지 않습니다.

이런 메시지는 재시도하지 않고 바로 DLT로 보내는 것이 더 효율적일 수 있습니다.

## 4. DLQ(Dead Letter Queue)는 무엇인가요?

DLQ는 Dead Letter Queue의 약자로, 정상적으로 처리할 수 없는 메시지를 별도로 보관하는 공간 또는 패턴을 의미합니다.

여기서 DLT와 DLQ를 구분해 보겠습니다.

| 구분        | DLT                          | DLQ                 |
| --------- | ---------------------------- | ------------------- |
| 정식 명칭     | Dead Letter Topic            | Dead Letter Queue   |
| 주로 쓰이는 맥락 | Kafka                        | 메시지 큐 시스템 전반        |
| 의미        | 실패 메시지를 저장하는 Kafka Topic     | 실패 메시지를 격리하는 논리적 공간 |
| 관계        | DLQ 패턴을 Kafka Topic으로 구현한 형태 | 더 넓은 개념             |

엄밀하게 말하면 DLT는 Kafka에서 사용하는 구현 형태이고, DLQ는 메시지 브로커 전반에서 사용하는 일반적인 개념입니다.

따라서 Kafka 기술 문서에서는 `DLT`라는 용어를 사용하는 편이 더 명확합니다.

## 5. Retry Topic과 DLT를 언제 사용할까요?

모든 예외에 무조건 재시도를 적용하면 안 됩니다.

실패 원인을 크게 두 가지로 나눠야 합니다.

### ① 일시적인 오류(Transient Error)

시간이 지나면 정상적으로 복구될 가능성이 있는 오류입니다.

예시:

- PostgreSQL 일시적 연결 장애
- 네트워크 통신 오류
- 외부 결제 API의 일시적 응답 실패
- 외부 서비스의 HTTP 503 응답

이런 오류는 Retry Topic으로 재시도하는 것이 적절합니다.

### ② 영구적인 오류(Permanent Error)

시간이 지나도 동일한 요청을 반복한다고 해결되지 않는 오류입니다.

예시:

- 필수 필드 누락
- 잘못된 상품 ID
- 지원하지 않는 이벤트 형식
- 유효하지 않은 주문 상태 전이

이런 오류는 재시도보다 DLT로 보내 원인을 분석하는 것이 적절합니다.

<img width="802" height="340" alt="image" src="https://github.com/user-attachments/assets/56be356c-f96e-4b0f-8707-afd634b209be" />


다만 오류를 일시적 오류와 영구적 오류로 분류하는 기준은 서비스마다 다릅니다. 예를 들어 HTTP 500도 특정 요청의 잘못된 데이터 때문에 발생했다면 재시도해도 해결되지 않을 수 있습니다.

## 6. Spring Kafka에서는 어떻게 구현할까요?

Spring Kafka에서는 `@RetryableTopic`과 `@DltHandler`를 이용해 Retry Topic과 DLT를 구현할 수 있습니다.

### ① 기본 Consumer

```
@Component
public class OrderConsumer {

    @RetryableTopic(
        attempts = "4",
        backoff = @Backoff(
            delay = 5000,
            multiplier = 2.0
        ),
        dltTopicSuffix = "-dlt"
    )
    @KafkaListener(
        topics = "order-topic",
        groupId = "inventory-service"
    )
    public void consume(OrderCreatedEvent event) {

        // PostgreSQL 재고 차감
        inventoryService.decreaseStock(event);
    }

    @DltHandler
    public void handleDlt(OrderCreatedEvent event) {

        // 최종 실패 메시지 기록 및 알림
        log.error("주문 이벤트 최종 처리 실패: {}", event);
    }
}
```

학습용 예시입니다. 실제 프로젝트에서는 Spring Kafka 버전, 토픽 설정, 예외 분류, 트랜잭션 구성 등을 추가로 검토해야 합니다.

코드를 하나씩 살펴보겠습니다.

`@RetryableTopic`

```
@RetryableTopic(
    attempts = "4",
    backoff = @Backoff(
        delay = 5000,
        multiplier = 2.0
    ),
    dltTopicSuffix = "-dlt"
)
```

- `attempts = "4"`: 최초 처리를 포함한 총 처리 시도 횟수입니다.
- `delay = 5000`: 최초 재시도 대기 시간은 5초입니다.
- `multiplier = 2.0`: 재시도 대기 시간을 2배씩 늘립니다.
- `dltTopicSuffix = "-dlt"`: DLT Topic 이름에 붙일 접미사입니다.

이 설정을 적용하면 재시도 토픽들이 생성되어 사용됩니다. 구체적인 토픽 이름과 생성 방식은 Spring Kafka 버전 및 설정에 따라 달라질 수 있습니다.

`@DltHandler`

```
@DltHandler
public void handleDlt(OrderCreatedEvent event) {
    log.error("주문 이벤트 최종 처리 실패: {}", event);
}
```

재시도 횟수를 초과해 DLT로 전달된 메시지를 처리하는 메서드입니다.

여기서는 로그를 남기는 간단한 예시지만 실제 운영에서는 다음 작업도 고려해야 합니다.

- 실패 이벤트 별도 저장
- 운영자 알림
- 실패 원인과 이벤트 ID 기록
- 재처리 가능 여부 판단

### ② PostgreSQL 처리 시 특히 주의할 점

Retry Topic을 사용한다고 해서 중복 처리가 사라지는 것은 아닙니다.

예를 들어 다음과 같은 상황이 발생할 수 있습니다.

1. Consumer가 PostgreSQL에서 재고 차감에 성공합니다.
2. Consumer가 Kafka Offset을 Commit하기 전에 장애가 발생합니다.
3. Kafka가 동일 메시지를 다시 전달합니다.
4. Consumer가 재고를 또 차감할 수 있습니다.

따라서 다음과 같은 멱등성 처리가 필요합니다.

```
CREATE TABLE processed_events (
    event_id VARCHAR(100) PRIMARY KEY,
    processed_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

이벤트 ID를 기본 키로 관리하면 동일 이벤트의 중복 처리를 방지하는 데 활용할 수 있습니다.

단, 단순히 이벤트 처리 전에 존재 여부만 조회해서는 동시 처리 경쟁 상태가 생길 수 있습니다. 실제 구현에서는 PostgreSQL의 UNIQUE 제약조건과 `INSERT ... ON CONFLICT` 등을 활용해 중복 처리를 원자적으로 통제해야 합니다.

## 7. DLT 메시지를 다시 처리할 수 있나요?

네. 가능합니다. 이를 \*\*DLT Replay(재처리)\*\*라고 합니다.

예를 들어 주문 1001의 재고 차감이 실패해 DLT로 이동했다고 가정하겠습니다.

운영자가 확인해 보니 원인은 PostgreSQL 서버 장애였습니다.

서버 복구 후 DLT에 보관된 메시지를 다시 원래 Topic 또는 재시도 Topic으로 발행하면 됩니다.

```
order-dlt
    |
    | 운영자 원인 분석
    v
PostgreSQL 장애 복구
    |
    v
DLT 메시지 재발행
    |
    v
order-topic
    |
    v
Inventory Consumer
    |
    v
재고 차감 처리
```

다만 재처리할 때도 주의해야 합니다.

- 이미 정상 처리된 이벤트인지 확인해야 합니다.
- 이벤트 ID를 유지해 중복 처리 여부를 검사해야 합니다.
- 원본 메시지의 실패 이력과 재처리 이력을 남기는 것이 좋습니다.
- 재처리한 메시지가 다시 실패하면 DLT로 돌아갈 수 있도록 설계해야 합니다.

## 9. 핵심 개념 최종 비교

| 개념          | 핵심 역할                  |
| ----------- | ---------------------- |
| Kafka Topic | 이벤트 저장 및 전달            |
| Partition   | 메시지 분할 저장과 병렬 처리       |
| Consumer    | 메시지를 가져와 업무 처리         |
| Offset      | Partition에서 메시지를 읽은 위치 |
| Retry Topic | 실패 메시지 재시도             |
| DLT         | 최종 실패 메시지 격리           |
| DLQ         | 실패 메시지를 격리하는 일반적인 패턴   |
| 멱등성         | 동일 메시지의 중복 처리 방지       |
| Saga        | 분산 업무 흐름 및 보상 트랜잭션 관리  |

꼭 기억할 세 가지입니다.

1. Retry Topic은 실패 메시지를 다시 처리하기 위한 장치입니다.
2. DLT는 반복해도 처리되지 않는 메시지를 무한정 재시도하지 않도록 격리하는 장치입니다.
3. Retry Topic과 DLT를 사용하더라도 중복 처리는 발생할 수 있으므로 멱등성이 필요합니다.

## 10. 이해도 확인 문제
