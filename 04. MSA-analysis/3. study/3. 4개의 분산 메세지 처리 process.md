둥실님, 지금 설명하신 내용에서 전체적인 흐름은 상당히 잘 잡으셨습니다. 다만 한 가지 중요한 부분이 뒤섞여 있습니다.

바로 Transaction Outbox와 Debezium CDC의 역할 순서입니다.

Transaction Outbox가 DB 변경 이력을 감지해서 이벤트를 만드는 것이 아닙니다. 애플리케이션이 비즈니스 작업을 수행할 때 이벤트를 Outbox 테이블에 함께 기록하고, Debezium이 그 Outbox 테이블의 변경 로그를 읽어서 Kafka로 전달하는 구조입니다.

이 차이를 이해하면 네 가지 기술의 관계가 명확해집니다.

# 1. 네 가지 기술의 전체 프로세스

먼저 네 기술이 어떻게 연결되는지 전체 그림부터 보겠습니다.

<img width="629" height="739" alt="image" src="https://github.com/user-attachments/assets/d16a0b53-1571-4bac-96c0-13f702166f41" />

여기서 Saga는 다른 네모 칸처럼 메시지가 지나가는 중간 장치가 아닙니다.

Saga는 여러 서비스에 걸친 업무 흐름을 관리하는 패턴입니다. 각 서비스가 Kafka 이벤트를 주고받으면서 Saga 흐름을 진행할 수 있습니다.

# 2. 이해 내용 검사

작성하신 네 가지 단계를 하나씩 살펴보겠습니다.

## ① 오더 테이블에서 변경 이력 발생

방향은 맞습니다

예를 들어 주문 서비스에서 주문을 생성합니다.

```
INSERT INTO orders
(order_id, customer_id, status)
VALUES
(1001, 10, 'PENDING');
```

이때 주문 DB에 데이터가 저장되고 DB의 트랜잭션 로그에도 변경 내용이 기록됩니다.

다만 Outbox 패턴을 사용한다면 이와 동시에 Outbox 테이블에도 이벤트를 기록합니다.

```
INSERT INTO outbox
(event_id, aggregate_type, aggregate_id,
 event_type, payload)
VALUES
('evt-001', 'Order', '1001',
 'OrderCreated', '{...}');
```

두 INSERT는 동일한 DB 트랜잭션 안에서 수행합니다.

즉, 주문 데이터와 이벤트 기록이 함께 성공하거나 함께 실패합니다.

## ② Debezium CDC가 테이블 로그를 보고 변경 이력 감지

맞습니다

Debezium은 DB의 트랜잭션 로그를 읽습니다.

다만 중요한 차이가 있습니다.

- 일반 CDC: orders 테이블의 변경을 직접 감지
- Outbox CDC: outbox 테이블의 변경을 감지

지금 설명하는 네 기술의 결합 구조에서는 두 번째 방식을 사용하는 것입니다.

## ③ Transaction Outbox가 그 이력을 이벤트 로그에 기록하고 Kafka에 전달?

이 부분은 수정해야 합니다.

여기서 역할이 반대로 이해되었습니다.

정확한 순서는 다음과 같습니다.

1. 주문 서비스가 주문 데이터를 변경합니다.
2. 주문 서비스가 Outbox 테이블에 비즈니스 이벤트를 기록합니다.
3. Debezium이 Outbox 테이블의 DB 변경 로그를 감지합니다.
4. Debezium Connector가 이벤트를 Kafka Topic으로 발행합니다.
5. Kafka가 해당 이벤트를 저장합니다.

Outbox는 Kafka에 전달하는 중계 프로그램이 아니라, 전달해야 할 이벤트를 DB에 안전하게 기록해 두는 저장 방식입니다.

## ④ 이벤트를 보고 해당 테이블의 변경 이력을 구독한 Consumer들에게 전달

개념적으로 맞습니다

다만 Consumer가 구독하는 대상은 일반적으로 테이블 자체가 아니라 Kafka Topic입니다.

예를 들어 다음과 같습니다.

- 결제 서비스 → `order-created` Topic 구독
- 재고 서비스 → `order-created` Topic 구독
- 배송 서비스 → 배송 시작에 필요한 이벤트 Topic 구독

Consumer는 메시지를 전달받아 각자의 업무를 수행합니다.

여기서 중요한 점은 Kafka가 Consumer에게 메시지를 강제로 밀어 넣는 방식만 사용하는 것은 아니라는 것입니다. 일반적인 Kafka Consumer는 Broker에 메시지를 요청하여 가져오는 Pull 방식으로 동작합니다.

# 3. Kafka Topic과 Partition은 대체 무슨 작업을 하는가?

이 부분이 사실 가장 중요합니다.

우선 다음 두 개념을 구분하셔야 합니다.

- Topic: 어떤 종류의 메시지를 모아 놓을 것인가?
- Partition: 그 메시지들을 어떻게 나누어 저장하고 병렬로 처리할 것인가?

예를 들어 주문 이벤트를 처리하는 `order-topic`이 있다고 가정하겠습니다.

## 3-1. Topic에 메시지가 저장되는 과정

주문 서비스에서 다음과 같은 이벤트가 발생했다고 가정하겠습니다.

| 주문 번호 | 이벤트          |
| ----- | ------------ |
| 1001  | OrderCreated |
| 1002  | OrderCreated |
| 1003  | OrderCreated |
| 1004  | OrderCreated |
| 1005  | OrderCreated |

이 메시지들이 Kafka의 `order-topic`에 저장됩니다.

그런데 주문이 초당 수천 건씩 발생한다면 하나의 Partition에서만 처리하는 것보다 여러 Partition으로 나누는 것이 효율적일 수 있습니다.

## 3-2. Partition으로 나누는 이유

<img width="649" height="378" alt="image" src="https://github.com/user-attachments/assets/f787d4bd-5e20-4ae7-a21a-c8b6d9cfdbe0" />


이렇게 나누는 이유는 메시지 처리 작업을 여러 Consumer가 동시에 수행할 수 있도록 하기 위해서입니다.

그렇다면 실제로 어떤 작업을 하는 걸까요?

예를 들어 주문 이벤트를 받은 결제 서비스는 다음 작업을 수행할 수 있습니다.

1. 주문 정보 확인
2. 결제 가능 여부 확인
3. 결제 승인 요청
4. 결제 결과 DB 저장
5. 결제 완료 이벤트 발행

재고 서비스는 다음과 같은 작업을 수행할 수 있습니다.

1. 주문 상품 확인
2. 상품별 재고 확인
3. 재고 차감 또는 예약
4. 재고 처리 결과 DB 저장
5. 재고 확보 완료 이벤트 발행

즉, Partition이 직접 업무를 수행하는 것은 아닙니다.

Partition은 메시지를 나누어 저장하는 단위이고, Consumer가 그 메시지를 읽어서 실제 업무를 수행합니다.

### 3-3. Partition을 나누면 무조건 빠를까?

그렇지는 않습니다.

예를 들어 Partition이 3개인데 Consumer가 5개라면 동일한 Consumer Group에서는 동시에 작업할 수 있는 Consumer가 최대 3개입니다.

반대로 Partition이 3개이고 Consumer가 1개라면 하나의 Consumer가 세 Partition을 처리해야 합니다.

또한 같은 주문에 관한 이벤트는 순서가 중요할 수 있습니다.

예를 들어 주문 1001번에 다음 이벤트가 발생했다고 가정하겠습니다.

```
OrderCreated
     ↓
PaymentCompleted
     ↓
InventoryReserved
     ↓
OrderConfirmed
```

이 순서가 뒤바뀌면 문제가 생길 수 있습니다.

따라서 주문 번호 `order_id`를 메시지의 Key로 지정하면 같은 주문의 메시지가 같은 Partition에 배정되도록 할 수 있습니다.

이렇게 하면 해당 Partition 안에서 메시지 순서를 유지할 수 있습니다.

단, 같은 Partition이라도 서로 다른 Consumer Group에서 독립적으로 소비할 수 있고, 업무 처리 완료 순서까지 자동으로 보장하는 것은 아닙니다.

# 4. 테이블 변경이 아닌 다른 이벤트에는 무엇이 있을까?

아주 좋은 질문입니다.

여기서 중요한 개념을 하나 짚고 넘어가겠습니다.

Kafka에서 다루는 이벤트는 반드시 데이터베이스 테이블의 변경 이벤트일 필요가 없습니다.

이벤트는 시스템에서 발생한 의미 있는 사건을 표현합니다.

크게 다음과 같이 생각하면 됩니다.

## 4-1. 데이터 변경 이벤트

데이터베이스에 실제 변경이 발생한 경우입니다.

| 이벤트               | 의미          |
| ----------------- | ----------- |
| OrderCreated      | 주문 데이터 생성   |
| OrderUpdated      | 주문 정보 변경    |
| OrderCancelled    | 주문 취소 상태 변경 |
| ProductRegistered | 상품 등록       |
| StockAdjusted     | 재고 수량 변경    |

이러한 이벤트는 Debezium CDC로 감지할 수 있습니다.

단, 일반 CDC는 DB 행의 변경 사실을 감지하는 것이고, `OrderCancelled`처럼 비즈니스 의미를 명확히 표현하려면 애플리케이션이 Outbox에 해당 이벤트를 직접 기록하는 것이 일반적입니다.

## 4-2. 업무 이벤트 (Business Event)

DB 변경 자체보다 업무적으로 중요한 사건을 표현합니다.

예를 들어 다음과 같습니다.

| 이벤트                | 의미       |
| ------------------ | -------- |
| PaymentApproved    | 결제 승인 완료 |
| PaymentFailed      | 결제 실패    |
| InventoryReserved  | 재고 확보 완료 |
| ShipmentDispatched | 배송 출발    |
| DeliveryCompleted  | 배송 완료    |
| CouponIssued       | 쿠폰 발급 완료 |

이 이벤트들은 실제 DB 변경을 수반하는 경우가 많지만, DB 변경 자체와 비즈니스 이벤트는 동일한 개념이 아닙니다.

예를 들어 재고 수량이 100개에서 90개로 변경되었다고 해보겠습니다.

이 변경이 발생한 이유는 다양할 수 있습니다.

- 고객 주문에 따른 재고 차감
- 상품 파손으로 인한 재고 조정
- 창고 간 재고 이동
- 재고 실사 결과 반영

모두 DB에서는 재고 수량이 변경된 것이지만 업무적으로는 서로 다른 사건입니다.

## 4-3. 시스템 이벤트

비즈니스 데이터 변경이 아닌 시스템 내부에서 발생하는 이벤트도 있습니다.

| 이벤트                   | 의미             |
| --------------------- | -------------- |
| ServiceStarted        | 서비스 시작         |
| ServiceUnavailable    | 서비스 이용 불가      |
| PaymentGatewayTimeout | 결제 PG 응답 시간 초과 |
| InventorySyncFailed   | 재고 동기화 실패      |
| DispatchRequested     | 자동 배차 요청       |
| DispatchAssigned      | 기사 배정 완료       |

이런 이벤트는 애플리케이션이나 인프라에서 발생할 수 있습니다.

다만 모든 시스템 로그를 Kafka로 보내야 한다는 뜻은 아닙니다. 이벤트의 목적과 처리 필요성에 따라 Kafka, 로그 수집 시스템, 모니터링 시스템 등을 구분해서 사용합니다.

## 4-4. DB 변경 없이 발생하는 이벤트도 있을까?

있습니다.

예를 들어 바로픽에서 다음 상황을 생각해 보겠습니다.

AI 자동 배차 요청

고객의 주문이 완료되고 상품 준비가 끝났습니다.

이제 배송 기사를 배정해야 합니다.

이때 배차 서비스가 다음과 같은 이벤트를 발생시킬 수 있습니다.

```
{
  "eventType": "DispatchRequested",
  "orderId": 1001,
  "mfcId": "MFC-01",
  "deliveryAddress": "경기도 오산시",
  "requestedAt": "2026-11-04T18:00:00"
}
```

이 이벤트는 DB 테이블 변경을 감지해서 만들어지는 것이 아닙니다.

애플리케이션이 배차 요청이라는 업무 사건을 인식하고 직접 이벤트를 생성하는 것입니다.

이 이벤트를 Kafka에 발행하면 배차 서비스의 Consumer가 받아서 기사 배정 알고리즘을 실행할 수 있습니다.

정리하면 다음과 같습니다.

| 이벤트 발생 방식  | 이벤트 생성 주체    | Kafka 전달 방식                    |
| ---------- | ------------ | ------------------------------ |
| DB 변경 감지   | Debezium CDC | Kafka Connect                  |
| 업무 이벤트 발생  | 애플리케이션       | Kafka Producer 또는 Outbox + CDC |
| 시스템 이벤트 발생 | 애플리케이션·인프라   | Kafka Producer 등               |

여기서 한 가지 더 구분해야 합니다.

DB 변경이 없는 이벤트는 반드시 Outbox를 사용하지 않아도 됩니다. 하지만 해당 이벤트의 발행과 다른 DB 작업 사이에 원자성이 필요하다면 Outbox를 고려할 수 있습니다.

# 5. 그렇다면 Saga는 이 과정에서 정확히 무슨 일을 할까?

마지막으로 Saga를 다시 연결하겠습니다.

Kafka가 메시지를 전달한다고 해서 주문부터 배송까지의 업무가 자동으로 올바르게 진행되는 것은 아닙니다.

각 서비스의 업무가 성공했는지, 실패했는지 판단하고 다음 작업을 결정하는 로직이 필요합니다.

이것이 Saga의 역할입니다.

예를 들어 Orchestration 방식이라면 다음과 같습니다.

<img width="642" height="468" alt="image" src="https://github.com/user-attachments/assets/b94d001f-c85d-4509-9aec-ebc8c4b393ef" />


여기서 중요한 것은 Saga가 반드시 Orchestrator 하나로 구현되는 것은 아니라는 점입니다. Choreography 방식에서는 각 서비스가 이벤트를 구독하고 다음 이벤트를 발행하면서 전체 흐름을 진행합니다.

# 6. 최종 정리: 네 기술의 담당 업무

이제 네 가지를 정확하게 구분해 보겠습니다.

| 기술                 | 담당하는 질문                                |
| ------------------ | -------------------------------------- |
| Saga               | 여러 서비스의 업무가 어떤 순서로 진행되고 실패하면 어떻게 복구할까? |
| Transaction Outbox | DB 저장과 이벤트 기록이 서로 어긋나지 않게 하려면?         |
| Debezium CDC       | DB에 기록된 이벤트를 어떻게 감지하고 추출할까?            |
| Kafka              | 추출된 이벤트를 어떻게 저장하고 여러 서비스에 분산할까?        |

전체 흐름을 한 문장으로 정리하면 다음과 같습니다.

> 서비스에서 업무가 발생하면 Transaction Outbox를 통해 DB 데이터와 이벤트를 함께 저장하고, Debezium CDC가 DB 변경 로그를 읽어 Kafka에 이벤트를 전달합니다. Kafka는 해당 이벤트를 Topic과 Partition에 저장하고 Consumer들에게 분산 전달하며, Saga는 이러한 이벤트와 명령을 활용해 여러 서비스에 걸친 업무 흐름과 실패 복구를 관리합니다.

## 7. 추가 학습 포인트

지금 단계에서는 아래 세 가지를 더 공부하시면 좋겠습니다.

1. Kafka의 메시지 Key와 Partition: 같은 주문의 이벤트가 왜 같은 Partition에 들어가야 하는지, 메시지 순서가 왜 중요한지.
2. Consumer의 Offset과 Commit: Consumer가 메시지를 처리했다는 사실을 Kafka가 어떻게 기록하는지.
3. 중복 메시지와 멱등성: 동일한 결제 이벤트가 두 번 전달되면 결제가 두 번 실행되지 않도록 어떻게 방지하는지.

특히 2번과 3번은 실무에서 매우 중요합니다.

Kafka가 메시지를 전달했다고 해서 Consumer의 업무 처리까지 정확히 한 번만 실행된다는 보장은 없습니다. 그래서 메시지 재처리, 중복 방지, 멱등성까지 함께 설계해야 합니다.

제 생각에는 다음 학습 주제는 Consumer Offset과 Commit이 가장 좋겠습니다. Partition을 왜 나누는지 이해하셨다면 이제 Consumer가 메시지를 어디까지 처리했는지 어떻게 관리하는지 이해할 차례입니다. 😊
