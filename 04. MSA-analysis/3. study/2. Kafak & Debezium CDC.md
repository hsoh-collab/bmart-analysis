# 메세지 분산처리에서 Kafak & Debezium CDC가 하는 일과 역할?
이 부분은 Kafka와 Debezium CDC를 각각 어떤 문제를 해결하기 위해 사용하는지 구분하면 이해하기 쉬워집니다.

먼저 핵심부터 말씀드리겠습니다.

- Kafka: 서비스 간 메시지를 전달하고, 저장하고, 여러 Consumer에게 분산하는 역할
- Debezium CDC: 데이터베이스에서 발생한 데이터 변경 사항을 감지하고 이벤트로 전달하는 역할

둘은 경쟁 관계가 아니라 서로 협력하는 기술입니다.

# 1. 메시지 분산 처리에서 Kafka와 Debezium CDC의 역할

MSA 환경에서 주문 서비스가 주문을 생성했다고 가정하겠습니다.

주문 정보가 변경되면 결제 서비스, 재고 서비스, 배송 서비스 등 다른 서비스에도 해당 변경 사실을 알려야 합니다.

그런데 각 서비스가 서로 직접 통신한다면 서비스 간 의존성이 높아지고, 서비스가 많아질수록 통신 관리도 복잡해집니다.

이때 Kafka와 Debezium CDC를 활용할 수 있습니다.

## 전체적인 메시지 전달 구조

이 구조에서 Debezium과 Kafka는 담당하는 일이 명확하게 다릅니다.

# 2. Debezium CDC의 역할

## 2-1. CDC란?

CDC는 Change Data Capture의 약자입니다.

우리말로는 변경 데이터 캡처라고 합니다.

데이터베이스에서 INSERT, UPDATE, DELETE 등의 데이터 변경이 발생하면 그 변경 사항을 감지하고 추출하는 기술입니다.

예를 들어 주문 테이블에 다음과 같은 데이터가 있다고 가정하겠습니다.

| order_id | status  | amount |
| -------- | ------- | ------ |
| 1001     | PENDING | 30000  |
| 1002     | PENDING | 45000  |

1001번 주문의 상태가 결제 완료로 변경됩니다.

```
UPDATE orders
SET status = 'PAID'
WHERE order_id = 1001;
```

이때 Debezium CDC가 DB의 변경 로그를 읽어 다음과 같은 변경 이벤트를 만들어 낼 수 있습니다.

```
{
  "op": "u",
  "before": {
    "order_id": 1001,
    "status": "PENDING"
  },
  "after": {
    "order_id": 1001,
    "status": "PAID"
  }
}
```

여기서 중요한 점은 Debezium이 매번 주문 테이블 전체를 조회하는 것이 아니라는 것입니다.

일반적으로 DB의 트랜잭션 로그를 읽어 변경 사항을 추적합니다.

- MySQL: Binlog
- PostgreSQL: WAL
- MongoDB: Oplog

즉, 데이터베이스 내부에서 발생한 변경 사항을 감지하여 외부 시스템이 활용할 수 있도록 전달하는 것입니다.

## 2-2. Debezium이 하는 일

Debezium의 역할을 정리하면 다음과 같습니다.

1. 데이터베이스 변경 로그를 읽습니다.
2. INSERT, UPDATE, DELETE 등의 변경 사항을 감지합니다.
3. 변경 데이터를 이벤트 형태로 변환합니다.
4. Kafka Connect를 통해 Kafka Topic으로 전달합니다.
5. 변경 이벤트를 외부 서비스가 활용할 수 있도록 합니다.

여기서 정확히 구분할 개념이 하나 있습니다.

Debezium은 CDC 기능을 수행하는 커넥터를 제공하는 기술이고, Kafka Connect는 커넥터를 실행하고 관리하는 프레임워크입니다.

Debezium 자체가 Kafka 브로커 역할을 하는 것은 아닙니다.

# 3. Apache Kafka의 역할

## 3-1. Kafka란?

Kafka는 대규모 데이터와 이벤트를 안정적으로 처리하기 위한 \*\*분산 이벤트 스트리밍 플랫폼(Distributed Event Streaming Platform)\*\*입니다.

쉽게 말하면 여러 서비스에서 발생한 메시지를 받아 저장하고, 필요한 서비스들이 가져갈 수 있도록 중간에서 전달하는 역할을 합니다.

Kafka는 단순히 메시지를 전달하고 삭제하는 중계 서버가 아닙니다.

메시지를 일정 기간 저장하고, 여러 Consumer가 독립적으로 메시지를 읽을 수 있도록 지원합니다.

## 3-2. Kafka의 주요 구성 요소

| 구성 요소          | 역할                            |
| -------------- | ----------------------------- |
| Producer       | Kafka에 메시지를 발행하는 주체           |
| Broker         | 메시지를 저장하고 전달하는 Kafka 서버       |
| Topic          | 메시지를 종류별로 구분하는 논리적 저장 공간      |
| Partition      | Topic을 여러 단위로 분할하여 병렬 처리 지원   |
| Consumer       | Kafka에서 메시지를 가져와 처리하는 주체      |
| Consumer Group | Consumer들을 그룹으로 묶어 메시지를 분산 처리 |

각 구성 요소를 주문 시스템에 적용해 보겠습니다.

### ① Producer

메시지를 Kafka에 발행하는 주체입니다.

예를 들어 Debezium CDC가 DB 변경 사항을 감지한 후 Kafka에 이벤트를 전달한다면 Debezium이 Producer 역할을 수행하는 셈입니다.

단, Kafka Connect의 Debezium 커넥터가 실제 Producer 동작을 수행합니다.

### ② Broker

Kafka 메시지를 저장하고 관리하는 서버입니다.

Kafka는 여러 Broker로 구성된 클러스터를 만들 수 있습니다.

하나의 Broker에 문제가 발생하더라도 Partition 복제본을 통해 장애에 대응할 수 있습니다.

### ③ Topic

메시지를 주제별로 분류하는 공간입니다.

예를 들어 다음과 같이 구성할 수 있습니다.

```
order-topic
payment-topic
inventory-topic
delivery-topic
```

주문과 관련된 메시지는 `order-topic`에 저장하고 결제와 관련된 메시지는 `payment-topic`에 저장하는 방식입니다.

### ④ Partition

Topic을 여러 개의 Partition으로 분할합니다.

이렇게 하면 여러 Consumer가 서로 다른 Partition을 처리하면서 병렬 처리를 수행할 수 있습니다.

예를 들어 다음과 같습니다.

```
order-topic
    |
    +-- Partition 0
    +-- Partition 1
    +-- Partition 2
```

### ⑤ Consumer

Kafka에서 메시지를 가져와 실제 업무를 수행하는 주체입니다.

예를 들어 결제 서비스가 `order-topic`을 구독하고 있다면 주문 생성 이벤트를 가져와 결제 작업을 수행할 수 있습니다.

### ⑥ Consumer Group

여러 Consumer를 하나의 그룹으로 묶어 메시지를 분산 처리합니다.

예를 들어 Consumer Group에 Consumer가 3개 있고 Partition도 3개라면 다음처럼 할당할 수 있습니다.

```
order-topic
    |
    +-- Partition 0 ---> Consumer 1
    +-- Partition 1 ---> Consumer 2
    +-- Partition 2 ---> Consumer 3
```

이렇게 작업을 나누면 여러 Consumer가 동시에 메시지를 처리할 수 있습니다.

여기서 중요한 규칙이 있습니다.

동일한 Consumer Group 안에서는 하나의 Partition을 동시에 여러 Consumer가 할당받아 처리하지 않습니다.

반대로 서로 다른 Consumer Group은 동일한 메시지를 각각 독립적으로 소비할 수 있습니다.

예를 들어 결제 서비스와 재고 서비스가 서로 다른 Consumer Group을 사용한다면 두 서비스 모두 동일한 주문 이벤트를 전달받을 수 있습니다.

## 3-3. Kafka가 하는 일

정리하면 Kafka는 다음과 같은 역할을 담당합니다.

1. Producer가 발행한 메시지를 수신합니다.
2. Topic과 Partition을 통해 메시지를 분류하고 저장합니다.
3. Consumer에게 메시지를 전달합니다.
4. Consumer Group을 활용해 병렬 처리를 지원합니다.
5. 메시지를 일정 기간 보관하고 재조회할 수 있도록 합니다.
6. 복제와 장애 대응 기능을 통해 메시지 처리의 안정성을 높입니다.

# 4. Debezium과 Kafka는 어떻게 협력하는가?

이제 둘의 관계를 연결해 보겠습니다.

앞서 살펴본 것처럼 Debezium은 데이터베이스의 변경 사항을 감지하고, Kafka는 그 변경 이벤트를 저장하고 전달합니다.

실제 동작 순서는 다음과 같습니다.

## 실제 동작 과정

1. 주문 서비스에서 주문 생성

   주문 서비스가 DB에 주문 정보를 INSERT합니다.
2. DB 트랜잭션 로그에 변경 기록

   DB가 Binlog 또는 WAL 등에 변경 사항을 기록합니다.
3. Debezium이 변경 사항 감지

   Kafka Connect에서 실행되는 Debezium Connector가 변경 로그를 읽습니다.
4. Kafka에 이벤트 전달

   Debezium Connector가 변경 정보를 Kafka Topic에 발행합니다.
5. Consumer가 메시지 수신

   결제 서비스, 재고 서비스 등 각 Consumer가 자신이 구독하는 이벤트를 가져옵니다.
6. 각 서비스에서 업무 처리

   결제 승인, 재고 확보 등 독립적인 작업을 수행합니다.

이 구조에서 Kafka와 Debezium이 없었다면 각 서비스가 DB 변경 사항을 다른 서비스에 전달하기 위해 직접 통신하거나 별도의 전달 체계를 구현해야 할 수 있습니다.

이 둘을 사용하면 데이터 변경 감지와 서비스 간 이벤트 전달을 분리할 수 있습니다.

# 5. Kafka와 Debezium CDC의 차이점 정리

| 구분     | Debezium CDC             | Apache Kafka                                 |
| ------ | ------------------------ | -------------------------------------------- |
| 핵심 역할  | DB 변경 감지                 | 메시지 저장 및 전달                                  |
| 주요 목적  | 데이터 변경 사항 추출             | 이벤트 스트리밍 및 분산 처리                             |
| 데이터 처리 | DB 로그 읽기                 | 이벤트 수신 및 저장                                  |
| 메시지 발행 | Kafka로 변경 이벤트 전달         | Producer 메시지 수신                              |
| 메시지 소비 | 직접적인 주요 역할 아님            | Consumer에게 메시지 제공                            |
| 병렬 처리  | CDC 작업 분산 지원             | Partition과 Consumer Group으로 지원               |
| 대표 구성  | Connector, Kafka Connect | Broker, Topic, Partition, Producer, Consumer |

## 6. 그렇다면 Kafka Connect는 무엇인가?

여기서 하나 더 알아야 할 기술이 있습니다.

바로 Kafka Connect입니다.

앞서 Debezium과 Kafka를 설명하면서 Kafka Connect가 등장했죠.

이 셋의 관계를 정확히 이해해야 합니다.

- Kafka: 메시지를 저장하고 전달하는 플랫폼
- Kafka Connect: Kafka와 외부 시스템 사이의 데이터 연결 및 전송을 관리하는 프레임워크
- Debezium: Kafka Connect에서 실행할 수 있는 CDC 커넥터를 제공하는 기술

예를 들어 다음과 같습니다.

```
       MySQL DB
           |
           | Binlog
           v
    Kafka Connect
           |
           +-- Debezium MySQL Connector
           |
           v
       Kafka Broker
           |
           v
       Kafka Topic
           |
           v
        Consumer
```

Kafka Connect는 Debezium Connector를 실행하고 관리합니다.

Debezium Connector는 MySQL의 Binlog를 읽고 변경 이벤트를 Kafka에 전달합니다.

Kafka는 전달받은 이벤트를 저장하고 Consumer에게 제공합니다.

## 7. 앞서 공부한 Saga와 Transaction Outbox까지 연결하기

지금까지 공부한 네 가지 개념을 하나로 연결하면 MSA 메시지 분산 처리의 큰 그림이 완성됩니다.

| 기술 및 패턴            | 담당하는 문제                |
| ------------------ | ---------------------- |
| Saga               | 여러 서비스에 걸친 트랜잭션과 실패 복구 |
| Transaction Outbox | DB 저장과 메시지 발행의 원자성     |
| Debezium CDC       | DB 변경 로그 감지 및 이벤트 추출   |
| Kafka              | 이벤트 저장, 전달, 분산 소비      |

실제 조합은 다음과 같습니다.

```
[주문 서비스]
      |
      v
[주문 DB]
      |
      +-- orders 테이블
      |
      +-- outbox 테이블
                |
                v
         [Debezium CDC]
                |
                v
          [Kafka Connect]
                |
                v
          [Kafka Broker]
                |
         +------+------+
         |      |      |
         v      v      v
       결제   재고    배송
       서비스 서비스 서비스
         |      |      |
         +------+------+
                |
          Saga 흐름 관리
          및 보상 트랜잭션
```

위 구조는 이해를 위한 개념도입니다. 실제로는 Kafka Connect와 Debezium Connector가 함께 실행되며, Saga 조정 방식에 따라 이벤트를 발행하고 소비하는 주체도 달라집니다.

특히 중요한 것은 Debezium CDC가 반드시 Transaction Outbox를 사용해야 하는 것은 아니라는 점입니다.

- 일반 CDC: 업무 테이블의 INSERT, UPDATE, DELETE를 직접 감지
- Outbox CDC: Outbox 테이블에 기록된 명시적인 업무 이벤트를 감지

MSA에서 업무 이벤트를 전달할 때는 Outbox CDC 방식이 변경된 DB 행과 비즈니스 이벤트를 구분하기 쉽다는 장점이 있습니다.
