Saga 패턴(Saga Pattern)과 트랜잭션 아웃박스(Transaction Outbox)는 MSA에서 분산 트랜잭션의 데이터 정합성을 보장하기 위해 사용하는 설계 패턴입니다.

다만 두 패턴은 해결하려는 문제가 다릅니다.

- Saga: 여러 마이크로서비스에 걸쳐 실행되는 트랜잭션을 어떻게 관리할 것인가?
- Transaction Outbox: 데이터베이스 변경과 메시지 발행 사이의 불일치를 어떻게 방지할 것인가?

쉽게 말하면 Saga는 여러 서비스의 작업 전체를 관리하는 패턴이고, Outbox는 하나의 서비스에서 DB 저장과 메시지 발행을 안전하게 연결하는 패턴입니다.

## 1. Saga 패턴 (Saga Pattern)

### 1-1. Saga란?

MSA에서는 각 마이크로서비스가 독립적인 데이터베이스를 사용합니다.

예를 들어 쇼핑몰에서 고객이 상품을 주문한다고 가정하겠습니다.

1. 주문 서비스: 주문 생성
2. 결제 서비스: 결제 승인
3. 재고 서비스: 재고 차감
4. 배송 서비스: 배송 요청

각 서비스는 자신의 데이터베이스에서 독립적으로 트랜잭션을 수행합니다.

그런데 결제까지 성공한 상황에서 재고 차감이 실패하면 어떻게 될까요?

하나의 DB를 사용하는 구조라면 전체 작업을 롤백할 수 있지만, MSA에서는 서로 다른 DB의 트랜잭션을 일반적인 RDBMS 롤백처럼 한 번에 취소할 수 없습니다.

이 문제를 해결하기 위해 Saga 패턴을 사용합니다.

### 1-2. Saga의 핵심 원리

Saga는 여러 개의 로컬 트랜잭션(Local Transaction)을 순차적으로 실행하고, 중간에 실패하면 이미 완료된 작업을 보상 트랜잭션(Compensating Transaction)으로 되돌리는 방식입니다.

예를 들어 다음과 같습니다.

주문 처리 Saga 예시

1. 주문 서비스

   주문 생성 → `PENDING`
2. 결제 서비스

   결제 승인 → 성공
3. 재고 서비스

   재고 차감 → 실패
4. 보상 트랜잭션 실행

   결제 취소 → 주문 상태 `CANCELLED`

최종 결과: 주문 취소 및 결제 복구

여기서 중요한 점은 보상 트랜잭션이 데이터베이스의 실제 롤백과 다르다는 것입니다.

이미 결제 승인이 완료되어 커밋된 상태이므로 DB 롤백으로 되돌리는 게 아니라, 별도의 결제 취소 작업을 실행하는 것입니다.

### 1-3. Saga의 두 가지 구현 방식

| 구분     | Choreography | Orchestration     |
| ------ | ------------ | ----------------- |
| 방식     | 이벤트 기반       | 중앙 조정자 기반         |
| 제어 주체  | 각 서비스        | Saga Orchestrator |
| 서비스 통신 | 이벤트 발행 및 구독  | 명령 전달 및 결과 수신     |
| 특징     | 중앙 통제자 없음    | 전체 흐름 관리          |
| 적합한 상황 | 단순한 업무 흐름    | 복잡한 업무 흐름         |

- Choreography(코레오그래피): 각 서비스가 이벤트를 발행하면 다음 서비스가 이를 구독하고 자신의 작업을 수행합니다.
- Orchestration(오케스트레이션): 별도의 조정자가 각 서비스에 작업을 지시하고 결과에 따라 다음 단계를 결정합니다.

## 2. 트랜잭션 아웃박스 (Transactional Outbox)

### 2-1. Transaction Outbox란?

이번에는 주문 서비스 내부에서 발생할 수 있는 다른 문제를 살펴보겠습니다.

주문 서비스가 주문을 생성하고 Kafka로 `OrderCreated` 메시지를 발행한다고 가정하겠습니다.

일반적으로 다음과 같이 작성할 수 있습니다.

```
@Transactional
public void createOrder(Order order) {
    orderRepository.save(order);

    kafkaTemplate.send("order-topic", order);
}
```

그런데 여기에는 문제가 있습니다.

DB 저장과 Kafka 메시지 발행은 서로 다른 시스템에서 수행되기 때문에 하나의 로컬 트랜잭션으로 묶이지 않습니다.

대표적인 문제 두 가지가 있습니다.

문제 1. DB 저장은 성공했지만 메시지 발행에 실패

1. 주문 DB 저장 성공
2. Kafka 브로커 장애 발생
3. 메시지 발행 실패

결과: 주문은 생성됐지만 다른 서비스는 주문 생성 사실을 알지 못합니다.

문제 2. 메시지 발행은 성공했지만 DB 저장에 실패

1. Kafka 메시지 발행 성공
2. DB 트랜잭션 롤백

결과: 주문은 존재하지 않는데 다른 서비스는 주문이 생성됐다는 메시지를 받습니다.

이처럼 두 시스템에 각각 기록하는 작업에서 발생하는 문제를 Dual Write Problem이라고 합니다.

### 2-2. Transaction Outbox의 핵심 원리

이 문제를 해결하기 위해 메시지를 곧바로 Kafka에 발행하지 않고, 먼저 DB의 `OUTBOX` 테이블에 저장합니다.

핵심은 비즈니스 데이터 저장과 OUTBOX 메시지 저장을 동일한 DB 트랜잭션으로 처리한다는 것입니다.

처리 과정은 다음과 같습니다.

## Transaction Outbox 처리 흐름

주문 서비스

주문 생성 요청

하나의 DB 트랜잭션 (@Transactional)

① 주문 테이블 저장

② OUTBOX 테이블에 이벤트 저장

두 작업 모두 성공해야 COMMIT

OUTBOX Relay

저장된 이벤트를 읽음

Kafka Broker

메시지 발행

Consumer 서비스

메시지 소비 및 후속 작업 수행

이렇게 하면 다음과 같은 효과가 있습니다.

- 주문 저장이 실패하면 OUTBOX 저장도 롤백됩니다.
- 주문 저장이 성공하면 OUTBOX 이벤트도 반드시 DB에 남습니다.
- Kafka가 일시적으로 장애가 발생해도 OUTBOX에 저장된 이벤트를 나중에 다시 발행할 수 있습니다.

즉, DB 저장과 이벤트 기록의 원자성을 보장합니다.&#x20;

### 2-3. OUTBOX 메시지를 Kafka로 전달하는 방법

OUTBOX에 메시지를 저장했다고 해서 Kafka로 자동 전송되는 것은 아닙니다.

OUTBOX 테이블에 저장된 메시지를 읽어 Kafka에 전달하는 별도 메커니즘이 필요합니다.

대표적으로 두 가지 방식이 있습니다.

| 방식                | 설명                                            |
| ----------------- | --------------------------------------------- |
| Polling Publisher | 일정 주기로 OUTBOX 테이블을 조회하여 미발행 메시지를 Kafka로 전달    |
| CDC               | DB의 변경 로그를 감지하여 OUTBOX에 새로 기록된 데이터를 Kafka로 전달 |

여기서 앞서 공부하셨던 Debezium CDC가 등장합니다.

예를 들어 다음과 같은 구조입니다.

```
주문 서비스
    |
    v
주문 DB
    |
    +-- orders 테이블
    |
    +-- outbox 테이블
            |
            v
       Debezium CDC
            |
            v
       Kafka Connect
            |
            v
       Kafka Topic
            |
            v
       Consumer
```

Debezium은 DB의 변경 로그를 읽어 OUTBOX 테이블의 변경 사항을 감지하고 Kafka로 전달할 수 있습니다.

주의할 점은 Debezium 자체가 메시지 전달의 중복을 완전히 없애주는 것은 아니라는 것입니다. 중복 전달 가능성이 있으므로 Consumer의 멱등성 처리도 필요합니다.&#x20;

## 3. Saga와 Transaction Outbox의 차이점

이제 두 패턴을 직접 비교해 보겠습니다.

| 비교 항목    | Saga                         | Transaction Outbox                 |
| -------- | ---------------------------- | ---------------------------------- |
| 해결하려는 문제 | 여러 서비스 간 분산 트랜잭션             | DB 저장과 메시지 발행 간 불일치                |
| 적용 범위    | 여러 마이크로서비스                   | 개별 서비스 내부                          |
| 핵심 원리    | 로컬 트랜잭션과 보상 트랜잭션             | DB와 OUTBOX 테이블의 원자적 저장             |
| 주요 구성 요소 | 참여 서비스, 조정자 또는 이벤트           | OUTBOX 테이블, Relay, 메시지 브로커         |
| 실패 처리    | 보상 트랜잭션 또는 재시도               | 메시지 재발행                            |
| 대표 기술    | Kafka, 메시지 브로커, Orchestrator | DB, Debezium, Kafka Connect, Kafka |

### 3-1. 가장 중요한 차이

두 패턴의 차이를 주문 시스템에 대입하면 명확해집니다.

Saga가 해결하는 문제

```
주문 서비스
    |
    v
결제 서비스
    |
    v
재고 서비스
    |
    v
배송 서비스

중간 단계에서 실패하면?
    |
    v
보상 트랜잭션 실행
```

여러 서비스에 걸친 주문 처리 전체의 성공과 실패를 관리합니다.

Transaction Outbox가 해결하는 문제

```
주문 서비스
    |
    +---- 주문 DB 저장
    |
    +---- 이벤트 DB 저장
                |
                v
           OUTBOX
                |
                v
              Kafka
```

주문 서비스에서 DB 저장은 성공했는데 Kafka 메시지 발행이 실패하는 문제를 방지합니다.

## 4. 두 패턴은 함께 사용할 수 있을까?

가능합니다. 실제로 함께 사용하면 좋습니다.

오히려 MSA에서 Saga를 안정적으로 구현하려면 Transaction Outbox를 함께 사용하는 경우가 많습니다.

예를 들어 다음과 같습니다.

## Saga + Transaction Outbox 결합 구조

① 주문 서비스

- 주문 생성
- OUTBOX에 OrderCreated 이벤트 저장

OUTBOX Relay → Kafka

② 결제 서비스

- OrderCreated 이벤트 수신
- 결제 승인
- OUTBOX에 PaymentCompleted 이벤트 저장

OUTBOX Relay → Kafka

③ 재고 서비스

- PaymentCompleted 이벤트 수신
- 재고 차감
- OUTBOX에 InventoryReserved 이벤트 저장

④ 주문 서비스

- InventoryReserved 이벤트 수신
- 주문 상태를 CONFIRMED로 변경

Saga 완료

만약 재고 차감이 실패하면 Saga가 보상 흐름을 실행합니다.

1. 재고 서비스에서 InventoryReservationFailed 이벤트 발행
2. 주문 서비스에서 실패 이벤트 수신
3. 결제 서비스에 결제 취소 명령 전달
4. 결제 서비스에서 결제 취소
5. 주문 상태를 CANCELLED로 변경

이 과정에서 각 서비스는 자신의 DB 변경과 다음 메시지 발행을 Transaction Outbox로 안전하게 처리할 수 있습니다.

단, 실제 구현에서는 중복 메시지 처리, 재시도, 타임아웃, 보상 작업의 실패까지 고려해야 합니다.

## 5. 최종적으로 기억해야 할 내용

# Saga

서비스와 서비스 사이의 문제

여러 서비스에 걸친 작업을 어떻게 진행하고, 실패하면 어떻게 복구할 것인가?

# Transaction Outbox

서비스 내부의 DB와 메시지 브로커 사이의 문제

DB 저장은 성공했는데 메시지 발행이 실패하는 상황을 어떻게 방지할 것인가?

그리고 한 가지 더 중요합니다.

- Saga는 Transaction Outbox를 대체하지 않습니다.
- Transaction Outbox도 Saga를 대체하지 않습니다.
- 두 패턴은 서로 다른 문제를 해결하므로 함께 사용할 수 있습니다.

발표할 때는 이렇게 설명하시면 됩니다.

> Saga는 여러 마이크로서비스에 걸친 분산 트랜잭션의 흐름과 실패 복구를 관리하는 패턴입니다. 반면 Transaction Outbox는 각 마이크로서비스 내부에서 DB 트랜잭션과 메시지 발행 사이의 데이터 불일치를 방지하는 패턴입니다. Saga를 구현하는 과정에서 서비스 간 메시지 전달의 신뢰성을 확보하기 위해 Transaction Outbox를 함께 사용할 수 있습니다.
