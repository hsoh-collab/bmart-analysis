# TMS 상세 비즈니스 로직 및 운영 기준

## 1. TMS의 정의·하위 시스템·협업 경계

TMS는 배송·이동 요청을 수신하여 **운송 계획, 배송 단위 구성, 배차, 배차 변경, 경로·ETA, 운송 관제**를 관리한다. **Delivery는 라이더가 실제로 수행한 픽업·운송·전달·회수 사실**을 소유한다. TMS의 배차 성공은 실물 인계나 배송 완료가 아니다. 고객 주문 원장은 OMS, 물리 재고 원장은 WMS가 DC/PPC별로 관리한다.

### 1.1 적용 범위와 거래·실물의 기준

TMS는 **DC→PPC 간선 운송과 PPC→고객 배송**의 운송 요청·차량/라이더 가용성·배송 단위·편성·배차·경로·ETA·재배차를 관리한다. 라이더 계정·앱·현장 픽업·고객 전달·회수의 실제 절차와 수행료 확정은 Delivery가 맡는다. 간선은 차량 운행의 실제 출발·도착·하차 결과를 수집하여 WMS/MFC 수령과 대사한다. 일회성 예약 주문의 도착 시간창은 포함하지만 정기구독 배송·요일별 반복 노선 자동 매칭은 초기 상세 범위에 넣지 않는다. DC4개 출고 회차를 사용하는 것과 반복 노선 최적화는 다르다.

SCM / Replenishment는 공급 필요·이관 승인, WMS는 공통 상품·DC/PPC 재고와 실제 출발/수령 반영, MFC Operations는 PPC 수령·검수·포장·현물 인계, OMS는 주문·취소·환불 판단을 확정한다. 관제 시스템은 사고·승인·고객 대응을 조율한다. TMS의 운송 종료가 PPC 재고 가산이나 고객 주문 전체 완료를 뜻하지 않는다. 외부 운송사 계약/API와 회계 정산·실제 입금 자동화는 구현 범위에서 제외하며 운영에 필요한 운송·배정 근거를 Delivery와 주관 원장에 전달한다.

명시적 팀 결정 외의 아래 운송/배차 상세는 `[설계안]`이다. 상용 제품 조사와 외부 배송 사례의 수치를 바로픽 확정 정책으로 간주하지 않는다.

외부 공급업체→DC 실제 입고·검수/구매발주는 초기 구현에서 제외하고 승인된 DC 초기 보유부터 운영한다. DC→PPC 보충과 고객 주문 이행은 포함한다. 센터 간 출발 후 실제DC반송/역이관·타PPC전환은 초기 제외다. 고객 반품/회수의 별도 승인 흐름과 혼동하지 않는다.

### 1.2 하위 시스템

| 하위 시스템 | 포함하는 비즈니스 로직 |
|---|---|
| 운송 기준정보 | 배송 권역·서비스 가능 지역·운송 수단·적재량·온도 조건·등록 수단 적합성·운영시간 |
| 운송 요청 접수 | OMS 고객 배송 및 SCM 거점 간 이동 요청 수신, 형식·중복·처리 가능 여부 검증 |
| 배송 단위 계획 | 주문과 배송 단위의 1:N 관계, 중량 10kg 초과 분할, 온도·적재 제약, 묶음 허용 조건 |
| 배송 유형·시간 창 | 즉시·예약·회수·반송·DC→PPC 운송 유형, 시간 창·마감·우선순위 |
| 배차 후보 선정 | 가용 라이더·권역·용량·업무 부하·현재 계정 제한을 조건으로 후보 탐색 |
| 배차 요청·수락 | 배차 제안, 유효기한, 라이더 수락·거절·타임아웃, 동시 수락 방지 |
| 재배차 | 노쇼·거절·지연·사고 발생 시 기존 배차 무효화, 후속 배차 이력 |
| 경로·ETA | 픽업·배송 순서·시간 추정·외부 지도 서비스 조회 및 실패 대체 |
| 운송 스케줄 | MFC 작업 완료 예정과 픽업 시간 조정, 혼잡·지연·인력 부족 대응 |
| 진행 상황 관제 | Delivery 수행 이벤트 기반 픽업·이동·도착 상태와 지연 원인 추적 |
| 운송 중단·변경 | OMS 취소 요청·현장 상황에 따른 중단 가능성 확인, Delivery에 실행 지시 |
| 회수·반송 운송 계획 | 회수지·목적 거점·운송 배정과 회수 작업 요청 |
| 운송 정산 근거 | 거리·배차·재배차·시간·취소 등 정산 기초 사실 |
| 연계 장애 복구 | 배차 이중 생성 방지, 수행 이벤트 지연·역전, ETA 서비스 장애, 미완료 운송 대사 |

각 행은 업무 범주이며 독립 마이크로서비스 수가 아니다. 상태의 최종 소유권·함께 확정할 수량/금액·실패 복구·운영 배포 경계를 기준으로 구현 단위를 정한다. 상위 범주에 반송·외부 입고·실제 자격 검증 등이 있어도 현재 제외된 실행을 자동 도입하지 않는다. 미설정 값은0/무제한으로 채우지 않고 영향 신규 업무만 보류한다.

### 1.3 다른 영역과의 협업

| 연계 영역 | 함께 정의해야 하는 업무 | 상대 영역이 소유하는 책임 |
|---|---|---|
| Commerce | 예상 도착·배차 정보·지연 이벤트 노출 | 고객 조회·알림·요청 화면 |
| 관제 시스템 | 배차 실패·지연 경보, 운영자 재배차·중단 요청 | 승인·권한·운영 개입 이력 |
| WMS | 출고 가능/인계 예정 수량, 운송 실물 식별자 | 재고 원장·인계 후 차감·반입 |
| OMS | 배송 생성·취소, 분할배송, 운송 상태 결과 | 주문 원장·취소 및 이행 판단 |
| SCM / Replenishment | DC→PPC 운송 물량·계획·지연 | 보충 수량·거점별 공급 결정 |
| MFC Operations | 픽업 준비 예상 시각, 대기·인계 지연 | 현장 피킹·포장·인계 작업 |
| Delivery | 배차 제안/확정·변경·중단 지시와 실제 수행 결과 대사 | 라이더 계정/앱·운행·실물 인수·전달·회수·수행료 |
| BI / Analytics | 배차 성공률·ETA 정확도·운송 지연 | 통계·성과 분석 |

상품 정본은 WMS이며 본사 상품/품질 승인 권한과 관제의 정책 승인 역할을 구분한다. 재고 예약은 OMS 요청을 WMS가 확정하고 시간대 슬롯은 MFC Operations가 확정한다. Delivery는 라이더 실제 수행을 소유하는 별도 시스템이며 현재 유효 배정과 수행 결과를 교환한다. BI / Analytics는 원천 사건/지표 협업만 유지하고 상세 구현·별도 최종 파일은 제외한다.

직접 조회/검증 요청, 확정 사건 수신, OMS/SCM 등을 통한 간접 조율을 구분한다. 모든 시스템을 직접 호출한다고 가정하지 않으며 상대 시스템이 담당하는 기능를 복제하지 않는다. 같은 요청·사건의 재전송은 원결과를 조회하고 다른 내용을 같은 요청으로 덮어쓰지 않는다. 성공한 원장 반영과 실패한 통지/조회 갱신을 분리해 미완료 단계만 복구한다.

[확정 정책] 상품 식별은 E-낱개/B-독립 실물 묶음과 전역 공통8자리 일련번호를 사용한다. DC/PPC는 같은 SKU를 쓰되 센터별 재고·예약·위치를 구분한다. 같은 기초상품의 구성 낱개 수 합산 기본10개 제한은 고객 구매에 적용하고 센터 간 보충에는 적용하지 않는다. BOX/PLT는 상품이 아닌 물류 취급 단위이며 E/B포장 전환은 초기 지원하지 않는다.


### 1.3.1 TMS 업무 범주와 기본 운송 흐름의 적용

TMS의 업무 범주는 운송 기준정보, 운송 요청 접수, 운송 계획, 적재·배송 단위 계획, 배차 후보 선정, 배차 요청·수락·확정, 출발지 준비·상차 확인, 운행 실행·추적, 운송 중 품질·사고 대응, 도착·하차·인계 결과 수집, 운송 변경·취소, 회수·반송 운송 계획, 운송 실적·정산 근거 관리, 운송 관제·복구로 구성한다. 이 범주는 업무 책임을 구분하기 위한 것이며, 각 항목을 별도 마이크로서비스로 분리해야 한다는 뜻은 아니다. 실제 구현 경계는 최종 상태 소유권, 수량·금액 확정 권한, 실패 복구 방식, 배포·운영 경계를 함께 고려해 결정한다.

기본 운송 흐름은 다음과 같다.

**운송 요청 접수 → 요청·자격·중복 검증 → 운송/배송 단위 구성 → 계획·적재·시간창 검증 → 후보 선정 및 차량·기사 편성 → 배차 제안·수락·확정 → 출발지 준비·실물 인계 확인 → 운송 실행 및 관제 → 도착·하차·수령 결과 수집 → 차이·잔여 의무 대사 → 운송 결과 종결 및 관련 원장·업무 영역에 결과 전달**

위 흐름에서 다음 세 가지는 서로 다른 업무 결과로 취급한다.

- **운송 요청:** 어떤 물품 또는 배송 의무를 어디에서 어디로, 언제까지 이동해야 하는가.
- **배차·운행 계획:** 어떤 차량 또는 라이더가 어떤 배송 단위와 방문 순서를 맡을 예정인가.
- **실물 인계·수행 사실:** 어떤 물품을 실제로 누가 인수했고, 어느 시각·장소에서 어떤 수량을 전달·회수했는가.

하나의 운송 요청은 여러 배송 단위로 분할될 수 있고, 하나의 차량 운행은 조건을 충족하는 복수 요청을 묶거나 여러 거점을 방문할 수 있다. 다만 고객 배송의 중량 분할 규칙, 간선의 한 요청 한 출발 규칙, 목적지·온도·용량·시간창 제약 등 해당 업무에 확정된 정책을 서로 대체해서는 안 된다. 배정 성공, 출발, 차량 도착, 하차, 수령 검수, 주문 이행, 재고 반영은 각각 별도의 사건이며 한 사건으로 다른 사건을 추정하거나 확정하지 않는다.

### 1.3.2 Commerce와의 상세 협업

**TMS 소유 업무**

- Commerce가 고객에게 노출할 수 있도록 현재 유효한 배차 여부, 배송 진행 상태, 최신 예상 도착 정보, 지연 또는 운송 중단의 영향 정보를 제공한다.
- 고객 배송별로 조회 가능한 운송 상태와 ETA를 구분해 제공하고, 계획 ETA·최신 예상 ETA·실제 수행 시각을 각각 보존한다.
- ETA 또는 배차 상태가 바뀌면 변경 사유와 발생 시각을 기록하고, Commerce가 오래된 정보를 최신 정보로 오인하지 않도록 버전·갱신 시각을 제공한다.
- 고객에게 공개할 수 있는 배송별 정보와 운영 내부 정보를 분리한다. 다른 고객의 주소, 라이더의 전체 경로, 타 배송의 상세정보 및 내부 사고 조사 정보는 고객 조회 응답에 포함하지 않는다.
- 지도·위치 정보가 불명확하거나 오래되었으면 도착 시각을 확정값처럼 노출하지 않고 확인 대기 또는 추정 정보로 표시할 수 있는 상태를 전달한다.

**Commerce 소유 업무**

- 고객용 배송 조회 화면, 주문 상세 화면의 운송 정보 표현, 고객 알림의 채널·문구·발송 시점 및 고객 문의 접수를 담당한다.
- 고객에게 어떤 정보를 어떤 표현으로 보여줄지 결정하되, TMS가 제공하지 않은 ETA나 운송 상태를 자체 추정해 확정 사실로 표시하지 않는다.
- 고객에게 보이는 안내가 필요하더라도 주문 취소·환불·예약 변경을 운송 이벤트만으로 확정하지 않는다. 주문·결제·고객 약속 변경은 해당 원장과 승인 흐름을 따른다.

**협업 요청·응답 및 실패 처리**

1. Commerce는 고객 주문 번호만으로 실물 운송을 임의 생성하지 않는다. 고객 배송 생성의 정본은 OMS이며, TMS는 OMS의 유효한 배송 요청과 연결된 운송 정보를 관리한다.
2. Commerce는 배송 조회 시 TMS가 제공하는 배송별 현재 상태·ETA·갱신 시각을 사용한다. 직접 조회가 불가능한 구성에서는 OMS 등 승인된 중계 영역을 통해 같은 정보를 전달받을 수 있으며, 모든 시스템이 서로 직접 호출해야 한다고 가정하지 않는다.
3. ETA 변경은 고객 약속 자체의 변경이 아니다. TMS는 영향과 최신 예상치를 제공하고, Commerce는 승인된 고객 안내 정책에 따라 노출·알림을 처리한다. 예약 약속 변경 여부는 OMS가 판단한다.
4. 동일한 지연 이벤트가 재전송되면 Commerce는 같은 사건을 중복 알림으로 만들지 않도록 사건 식별자·버전·발생 시각을 활용한다. TMS도 같은 원사건의 재전송으로 새 배송이나 새 배정을 만들지 않는다.
5. Commerce의 알림 발송 실패는 운송 실패와 별도로 기록한다. 알림 실패만으로 배정을 취소하거나 실제 운송 상태를 되돌리지 않는다.

**주요 검증 사례**

- ETA가 변경되었지만 OMS의 예약 약속은 아직 변경되지 않은 경우, 최신 예상 도착 정보와 확정 약속을 별개로 표시할 수 있어야 한다.
- 위치 정보가 오래된 경우, 부정확한 도착 시각을 확정 사실로 노출하지 않고 확인 대기 상태를 제공해야 한다.
- 동일 지연 이벤트가 반복 수신되어도 동일 고객에게 중복 알림을 무한 생성하거나 배송 상태를 역행시키지 않아야 한다.
- 고객이 화면에서 배송 취소를 요청하더라도 Commerce의 화면 동작만으로 운송·주문 취소를 확정하지 않고 OMS의 판단 결과를 기다려야 한다.

### 1.3.3 WMS와의 상세 협업

**TMS 소유 업무**

- WMS가 제공하는 출고 준비 정보, 출발지·목적지, 화물 식별자, SKU/LOT별 수량, BOX/PLT 등 취급 단위, 중량·부피·온도 조건을 운송 계획과 대조한다.
- 차량·구획·방문 순서·시간창·온도대·적재량 조건을 검증하고, 불일치나 필수 정보 미설정이 있으면 신규 편성 또는 출발을 보류한다.
- 상차·출발·하차·실물 인계의 운송 증빙을 수집·전달한다. TMS는 WMS가 소유한 재고 원장을 직접 차감·가산하거나 이동 중 재고를 독자적으로 확정하지 않는다.
- 계획 수량, 실제 상차 수량, 실제 하차·인계 수량, 목적지 실수령 수량과 차이를 서로 다른 값으로 보존한다.
- 운송 중 파손·온도 이탈·봉인 훼손·분실 의심·과부족이 발생하면 관련 화물, 운송, 차량, 정차지, 시각, 증빙을 연결해 WMS 및 관제·현장 운영의 대사를 지원한다.

**WMS 소유 업무**

- 상품 정본, DC/PPC별 물리 재고, 재고 예약·할당, 출고 가능 여부, 실제 출고 차감, 이동 중 재고 전환, PPC 입고·격리·폐기 등 재고 원장 반영을 담당한다.
- 실제 현물 수량과 재고 상태를 원장에 반영한다. TMS의 배정 확정·차량 출발 알림·도착 GPS만으로 재고를 변경하지 않는다.
- DC/PPC별 동일 SKU의 재고·예약·위치를 분리 관리하고, LOT 및 실물 단위 추적을 유지한다.
- 승인된 출고·수령·격리·폐기 결과를 원장에 반영하며, 동일 사건 재전송으로 재고를 중복 차감하거나 중복 가산하지 않는다.

**협업 요청·응답 및 실패 처리**

1. TMS는 운송 계획 전에 WMS의 최신 출고 준비·화물·수량 정보를 확인한다. 필수 정보가 없거나 최신 여부를 검증할 수 없으면 이를 0, 무제한 또는 적합으로 간주하지 않고 신규 계획·출발을 보류한다.
2. 출발 전에는 승인된 출고, 실제 상차, 차량·기사·목적지, 봉인 및 온도·적재 조건을 확인한다. 출발 사실과 증빙은 WMS에 전달하되, DC 현물 감소와 이동 중 전환은 WMS가 확정한다.
3. 도착·하차 이후 TMS는 실제 인계 화물·수량·시각·담당자·위치·사진 또는 봉인 증빙을 제공한다. MFC Operations가 현장 수령·검수 결과를 확정하고 WMS가 그 결과에 따라 정상·격리 재고와 이동 중 잔량을 반영한다.
4. 계획 수량과 실수령 수량이 다르면 TMS는 차이를 기록하고 대사 의무를 유지한다. 예정 수량을 실수령 수량으로 대체하지 않으며, 차이가 있다는 이유만으로 자동 손실·폐기·재고 조정을 하지 않는다.
5. 같은 출발·수령 사건이 재전송되면 WMS의 원장 반영 결과를 조회하고 미완료 통지 단계만 복구한다. 성공한 재고 반영을 다시 수행하지 않는다.
6. 고객 배송의 실제 픽업·전달 결과도 운송 상태만으로 WMS 재고 반영을 확정하지 않는다. 상품·포장·재고의 실제 상태와 권한 있는 현장/원장 사건을 사용한다.

**주요 검증 사례**

- 계획 100박스, 실제 상차 100박스, PPC 실수령 98박스이면 TMS는 2박스 차이를 기록하고 WMS·MFC Operations와 대사한다. 계획 수량 100박스를 수령 완료 수량으로 쓰지 않는다.
- 출발 48, 정상 인수 44, 격리 2, 미수령 2이면 실제 수령 46과 이동 중 잔량 2를 구분한다. 격리 2와 미수령 2를 같은 물량으로 중복 차감하지 않는다.
- 차량 GPS가 PPC에 도착했다고 보고하더라도 실제 하차·수령 결과가 없으면 입고 완료로 처리하지 않는다.
- WMS 반영은 성공했지만 TMS의 응답 수신이 실패한 경우, TMS는 원장 반영 여부를 조회하고 성공한 반영을 반복 요청하지 않는다.

### 1.3.4 OMS와의 상세 협업

**TMS 소유 업무**

- OMS가 확정한 고객 배송 요청을 수신하고 요청 식별자·버전·배송 주소/권역·배송 유형·예약 시간창·배송별 요구사항·취소 여부 등 운송 계획에 필요한 정보를 검증한다.
- 주문과 배송 단위의 관계를 유지하고, 배송 단위별 후보 탐색·제안·배정·재배정·ETA·실제 수행 결과를 관리한다.
- OMS 취소·중단 요청을 수신하면 현재 배정, 포장별 현장 인계 여부, Delivery의 실제 인수 여부를 대사하여 실행 중단·배정 해제·후속 운송 가능성을 판단한다.
- 배송별 성공·실패·미전달·부분 수행·회수 필요·현재 보관자 등 운송 결과를 OMS에 전달한다. 주문 전체 완료·취소·환불은 TMS가 확정하지 않는다.
- 배정 버전과 유효 시점을 관리하여 취소되거나 오래된 제안·배정이 늦게 수락되거나 다시 실행되는 것을 막는다.

**OMS 소유 업무**

- 고객 주문 원장, 주문 이행 여부, 주문 취소·환불·교환·재배송 승인, 고객 예약 약속, 주문별 배송 분할의 주문 관점 결과를 담당한다.
- 주문의 취소 가능 여부, 결제·환불 처리, 고객 약속 변경, 주문 전체 이행 완료 여부를 판단한다.
- TMS가 전달한 배송별 결과를 주문 단위의 나머지 의무와 결합해 판단하며, 일부 배송 성공만으로 전체 주문을 완료 처리하지 않는다.
- 재고 예약은 WMS와 협업해 확정하고, TMS의 운송 배정이나 ETA를 재고 예약 확정으로 간주하지 않는다.

**협업 요청·응답 및 실패 처리**

1. TMS는 OMS의 유효 배송 요청만 운송 계획의 기준으로 삼는다. 동일 OMS 요청이 다시 전달되면 원요청 계보와 기존 결과를 조회하고 중복 운송·배정을 만들지 않는다.
2. OMS가 취소를 요청하면 TMS는 배정 해제 가능성만 기계적으로 판단하지 않고 MFC Operations의 포장·인계 상태와 Delivery의 실물 수령 사실을 확인한다. 미인계가 확인된 경우 기존 기사 권한을 해제하고 후속 배차를 검토할 수 있다.
3. 실물 인계가 진행 중이거나 사실이 불명확하면 동일 포장을 새 기사에게 넘기지 않는다. 현장 판정과 실제 실수령·현재 보관자를 확인하고 안전한 회수 또는 승인된 재인계를 계획한다.
4. TMS는 배송별 결과와 미해결 의무를 OMS에 전달한다. 주문 전체 이행·취소·환불·예약 변경은 OMS의 확정 결과를 받아 반영한다.
5. 예약 시간 변경은 OMS가 새 슬롯·재고·기한·현장 여력을 확인해 확정한 경우에만 TMS 계획에 반영한다. 결제 후 주소·연락처·요청 사항 변경을 TMS가 임의로 허용하지 않는다.
6. 배송이 여러 건으로 분할된 경우 각 배송의 수행 결과를 독립적으로 전달한다. 한 배송 실패가 다른 배송의 성공 사실을 지우지 않으며, 한 배송의 성공이 주문 전체 완료를 자동 확정하지 않는다.

**주요 검증 사례**

- 주문 배송 2건 중 1건만 성공한 경우, OMS에는 배송별 결과가 각각 전달되고 주문·PG·환불·수행료가 자동 종결되지 않는다.
- OMS 취소 요청과 라이더의 실물 인계가 경합하면, 인계 사실을 확인하기 전 같은 포장을 다른 기사에게 재배정하지 않는다.
- 예약 변경 결과가 늦게 도착한 경우, 이전 배정 버전의 수락을 거부하고 OMS가 확정한 새 예약만 적용한다.
- 고객 취소 화면의 요청만으로 TMS가 실제 운송 종료나 환불을 확정하지 않는다.

### 1.3.5 SCM / Replenishment와의 상세 협업

**TMS 소유 업무**

- SCM이 승인한 DC→PPC 이관 요청을 수신하고 출발지·목적지·SKU/LOT·수량·필요 도착시간·우선순위·요청 버전 및 취소 여부를 검증한다.
- 승인된 이관 물량을 실제 운송 단위·차량·회차·정차 계획으로 구성하고 차량 용량, 중량·부피, 온도대, PPC 수령 창 및 작업 여력을 검증한다.
- 미배정·미출발·지연·수량 차이·사고를 감지하고 최신 ETA 및 공급 약속에 미치는 영향을 SCM에 전달한다.
- 한 이관 요청의 원계보, 실제 출발·도착·하차·수령 결과 및 미해결 수량을 유지한다. 운송 중이라는 이유만으로 공급 완료를 선언하지 않는다.

**SCM / Replenishment 소유 업무**

- 어떤 상품을 어느 거점에 얼마나, 언제까지 공급할지 결정하고 보충 수량·목적 PPC·우선순위·공급 필요 시각·이관 승인 및 공급 계획 변경을 소유한다.
- 운송 지연이 공급 필요·보호기간·후속 보충 계획에 미치는 영향을 평가하고, 수량·회차·목적지 등 원공급 계획을 바꿀 필요가 있으면 새 승인 또는 변경 요청을 발행한다.
- TMS가 전달한 운송 상태를 공급 이행 판단의 입력으로 사용하되, 단순 배차 성공이나 차량 도착만으로 보충 이행을 완료 처리하지 않는다.

**협업 요청·응답 및 실패 처리**

1. SCM은 승인된 이관 요청과 요청 버전을 제공한다. TMS는 같은 요청의 재전송을 신규 이관으로 중복 생성하지 않는다.
2. 현재 정책은 승인 요청 1건당 1회 출발을 기준으로 한다. 차량이 부족해 일부 물량만 수용할 수 있는 경우, 동일 요청을 여러 출발로 임의 분할하지 않고 계획을 보류한 뒤 SCM 및 관련 운영 담당자에게 수량·회차 재승인을 요청한다.
3. TMS는 DC 작업·출발 회차와 PPC 실제 수령·검수 창을 함께 검증한다. 수령 창이나 필수 한도가 미설정이면 신규 편성·출발을 보류하며, 미설정 값을 0분 또는 무제한으로 처리하지 않는다.
4. 운송 지연이 발생하면 최신 ETA와 영향 받는 이관·정차를 SCM에 전달한다. SCM은 공급 계획의 유효성·수량·우선순위를 재평가하고 필요한 변경을 승인한다. TMS는 SCM의 승인 없이 목적지를 바꾸거나 타 PPC 전환·역이관을 실행하지 않는다.
5. DC 출발 후 목적지 변경, 자동 역이관, 강제반송 및 실제 DC 반송은 초기 구현 범위에서 제외한다. 사고가 발생하면 현 위치·보관 책임·품질 상태를 기록하고 안전한 수령 및 차이 해결을 조율한다.
6. 운송 종료와 보충 이행 완료를 분리한다. PPC의 실제 수령·검수와 WMS 재고 반영 결과가 확인되지 않으면 공급 완료를 추정하지 않는다.

**주요 검증 사례**

- 차량 용량이 부족해 승인 물량 전부를 싣지 못하는 경우, 일부 물량만 별도 출발로 자동 전환하지 않고 보류·재승인 절차를 따른다.
- ETA 지연으로 공급 필요 시각을 맞출 수 없을 가능성이 있으면 SCM에 영향 정보를 제공하되 공급 수량·목적지·필요 시각을 TMS가 임의로 변경하지 않는다.
- PPC 수령 창이 설정되지 않았으면 신규 출발을 보류하고 담당자 확인을 요청한다.
- 운송이 끝났더라도 실수령·검수·WMS 반영이 완료되지 않았다면 보충 완료로 처리하지 않는다.

### 1.3.6 MFC Operations와의 상세 협업

**TMS 소유 업무**

- PPC별 수령 가능 창, 작업 준비 예상, 픽업·상차·하차·인계에 필요한 시간 및 운송 계획에 영향을 주는 운영 제한을 조회하거나 전달받아 계획·배차·ETA에 반영한다.
- 간선 운송에서는 실제 차량 도착·하차·화물 인계 증빙을 전달하고, 현장 수령 결과와 차이를 대사한다.
- 고객 배송에서는 준비 예상 시각을 활용해 배차 제안을 시작할 수 있으나 실제 픽업은 포장 검품·현장 인계 완료 후 진행되도록 조율한다.
- 현장 지연·인계 불명·안전 제한이 발생하면 관련 배정을 보류·변경하고, 실제 인계 여부가 확인되기 전 동일 포장을 새 기사에게 넘기지 않는다.
- 최신 ETA와 도착 예정 정보를 제공해 PPC가 인력·보관·하차 준비를 조정할 수 있도록 한다.

**MFC Operations 소유 업무**

- PPC의 현장 피킹·포장·검품·준비 완료·출고 중지·현물 인계·수령·검수·적치 및 현장 작업 순서를 소유한다.
- PPC의 실제 수령 가능 시간, 시간대별 작업 여력, 도크·하차 여력, 현장 안전 제한과 재개 승인을 확정한다.
- 현장에서 실제로 인수한 수량·파손·품질·온도 관련 검수 결과와 현재 보관 위치·책임자를 확정한다.
- 현장 포장·수령 사실을 WMS의 재고 원장 반영과 연결하되, TMS 상태를 근거로 실물 검수 결과를 대체하지 않는다.

**협업 요청·응답 및 실패 처리**

1. TMS는 편성·배정·출발 직전에 최신 PPC 운영 제한과 수령 창을 확인한다. 과거에 정상으로 확인된 정보가 있더라도 더 최신의 안전 제한이 있으면 최신 제한을 적용한다.
2. MFC Operations가 포장 준비 예상 시각을 변경하면 TMS는 픽업 예상·기사 대기·후속 ETA를 재평가한다. 준비 예상은 실제 포장 완료나 인계 사실이 아니다.
3. 간선 차량이 도착하면 TMS는 도착·하차·인계 정보를 제공하고, MFC Operations는 실제 수령·검수 결과를 확정한다. 차량 도착만으로 수령 완료 처리하지 않는다.
4. 수령 창 미설정, 현장 혼잡, 인력 부족 또는 안전 제한이 있으면 신규 출발·픽업을 보류하거나 조정한다. 이미 운송 중인 화물은 과거 출발을 취소하는 대신 현재 위치·온도·보관 조건·누적 대기를 확인해 안전한 수령을 조율한다.
5. 현장 인계가 진행 중이거나 결과가 불명확한 상태에서는 배정 해제 성공 응답만으로 새 기사 실행을 허용하지 않는다. MFC Operations의 최종 현장 판정과 Delivery의 실제 인수 사실을 함께 확인한다.
6. PPC에서 격리·부적합이 확인된 물품은 정상 판매 가능 재고로 취급하지 않는다. TMS는 품질 사건과 인계 증빙을 연결하고, 격리·재고 반영·폐기 결정은 MFC Operations·WMS 및 권한 있는 품질 담당자의 절차를 따른다.

**주요 검증 사례**

- 포장이 아직 준비되지 않았어도 배정 계획을 유지할 수 있지만, 실제 픽업·재고 차감은 발생하지 않는다.
- PPC 수령 창이 미설정된 경우 새 출발을 보류한다. 이미 저온 화물이 도착했다면 안전한 보관·수령을 조율하고 자동 반송하지 않는다.
- 현장 인계가 불명확한 상태에서 배정 해제 응답이 도착해도, 같은 포장을 새 기사에게 중복 인계하지 않는다.
- MFC Operations가 실제 수령 수량을 98개로 확정한 경우 TMS는 계획 수량 100개로 덮어쓰지 않고 차이를 유지한다.

### 1.3.7 Delivery와의 상세 협업

**TMS 소유 업무**

- 운송 요청을 배송 단위로 구성하고, Delivery가 제공하는 라이더 가용성·등록 수단·활동 권역·위치 최신성·현재 수행·계정 제한 정보를 이용해 후보를 선정한다.
- 배차 제안·유효기한·수락·거절·만료·현재 유효 배정·배정 버전·재배차 및 전체 경로·ETA를 관리한다.
- Delivery에 배차 확정, 배정 변경, 실행 중단 또는 후속 회수·대체 배정 요청을 전달하고, 원배정과 실제 수행 결과를 대사한다.
- 배정과 실제 실물 인수·이동·전달·회수 사실을 별도로 보존한다. 실물 책임이 다른 수행자에게 실제로 인계되기 전에는 배정 변경만으로 책임자를 바꾸지 않는다.
- 제안·수락 당시 조건, 거리·배정·재배차·시간·지연·취소 등 운송 정산 기초 사실을 보존해 Delivery에 제공한다.

**Delivery 소유 업무**

- 라이더 계정·앱, 라이더의 실제 운행, 현장 픽업·실물 인수, 고객 전달, 미전달, 회수, 실제 수행 증빙과 수행료 확정·모의 지급을 소유한다.
- 라이더가 실제로 물품을 인수·전달·회수했는지, 현재 물품을 누가 보관하는지, 오프라인 수행·현장 사건이 무엇인지 확정해 TMS에 제공한다.
- 계정 상세 변경, 단말·운행 조작, 라이더 수행 증빙과 오프라인 이벤트를 관리한다. TMS는 전달받은 계정·수행 정보를 임의로 정상화하거나 실제 자격 검증 완료로 표시하지 않는다.
- 실제 면허·보험·계좌 소유 검증 및 실제 송금은 현재 프로젝트 범위에서 제외된다. 계정 정보가 입력되었다는 사실을 외부 자격 검증이나 지급 완료 사실로 표현하지 않는다.

**협업 요청·응답 및 실패 처리**

1. TMS는 후보 선정과 배정 직전에 Delivery의 최신 가용성·계정 제한·현재 수행·수단 적합성을 확인한다. 조회 불명이나 오래된 정상 응답만으로 신규 배정을 확정하지 않는다.
2. 배차 제안에는 픽업지, 배송 권역, 배송 방식, 예상 준비·운행 시간, 중량·부피·봉투·특별 조건, 승인된 수행료 조건 및 응답 기한을 전달한다. 상세 주소 등 민감 정보는 수행에 필요한 시점과 범위에 한해 제공한다.
3. 동일 배송에 대한 동시 수락은 한 명의 유효 기사만 확정한다. 늦은 수락은 만료·이미 배정·취소·자격 제한·용량 부족 등 실제 거절 사유를 구분해 처리한다.
4. Delivery의 실제 픽업·전달·회수 사건은 원배정·배송·포장·배정 버전과 연결한다. 이벤트가 늦게 오거나 순서가 뒤바뀌어도 실제 사건의 시각과 원결과를 보존하고 상태를 역행시키지 않는다.
5. 응답이 유실되면 새 배정을 생성하기 전에 기존 배정·수락·실행 지시 결과를 조회한다. 실제 배정 성공과 알림 실패를 구분하고, 알림 실패 때문에 성공한 배정을 취소·재생성하지 않는다.
6. 픽업 전 취소·노쇼·지연은 실제 인계 여부를 확인한 뒤 배정 해제·재배차를 결정한다. 픽업 후 사고는 현재 위치·보관 조건·실물 책임을 확인하고 실제 재인계가 확인된 후에만 후속 수행을 진행한다.
7. TMS는 수행료를 최종 확정하거나 지급하지 않는다. 제안·수락 당시 조건과 운송 실적 근거를 제공하고 Delivery가 소유하는 수행료 확정·모의 지급 결과와 구분한다.

**주요 검증 사례**

- 같은 배송을 두 라이더가 동시에 수락해도 유효 배정은 한 명에게만 확정되어야 한다.
- 라이더가 실제로 픽업했지만 픽업 이벤트 수신이 늦은 경우, 배정상 공백만을 근거로 다른 라이더에게 같은 포장을 재픽업시키지 않는다.
- 실제 전달 완료 뒤 늦은 도착 이벤트가 도착해도 완료 상태를 진행 중으로 되돌리지 않는다.
- 알림 전송 실패와 배정 실패를 구분하고, 이미 성공한 배정을 중복 생성하지 않는다.
- 사고 뒤 새 기사가 배정되더라도 물품의 실제 재인계와 원기사의 임무 종료를 별도 결과로 관리한다.

### 1.3.8 BI / Analytics와의 상세 협업

**TMS 소유 업무**

- 요청 접수·계획·배정·재배정·출발·도착·하차·인계·실패·지연·사고·수량 차이 등 원천 사건과 측정에 필요한 식별자·버전·시각·상태를 제공한다.
- 배차 성공률, 배정 소요시간, ETA 정확도, 정시 출발·도착률, 운송시간, 인수 차이, 사고·파손 건수, 재배차 횟수 및 운송 원가 산출에 필요한 근거 데이터를 일관된 정의로 전달한다.
- 계획값·최신 예상값·실제값과 취소·정정 이력을 구분해 제공한다. 이전 사건을 삭제하거나 최신 상태로 덮어써 과거 성과를 바꾸지 않는다.
- 지표 정의에 필요한 원천 데이터의 의미·분모·분자·제외 조건을 업무 담당자와 합의하고, 누락·중복·지연 사건을 식별할 수 있게 한다.

**BI / Analytics 소유 업무**

- 원천 사건을 이용한 통계 집계·성과 분석·대시보드·리포트·추세 분석을 담당한다.
- 지표 결과를 분석하고 운영 개선 기회를 제시하되, 분석 결과 자체가 배차·재고·주문·운송 사고의 업무 상태를 직접 변경하지 않는다.
- 데이터 모델·집계 방식·분석용 파생 지표는 분석 영역에서 관리하고, TMS 원천 사건의 의미를 승인 없이 재정의하지 않는다.

**협업 요청·응답 및 실패 처리**

1. TMS는 사건 발생 시각과 수신 시각, 원요청·배송·배정·운행 식별자, 버전, 사건 유형 및 정정 관계를 제공한다. BI는 계획·최신 예상·실제 수행을 같은 필드로 합쳐 하나의 값처럼 취급하지 않는다.
2. 이벤트 중복·지연·역순 수신은 원사건 식별자와 정정 이력을 이용해 집계에서 구분한다. 분석 적재 실패는 운송 실행이나 업무 원장 반영을 되돌리지 않는다.
3. ETA 정확도·정시 도착률의 기준 시각과 허용 오차, 취소·부분 수행·미전달 건의 분모 포함 여부는 BI와 업무 책임자가 정의를 합의해야 한다. 정의가 미결정이면 임의 수치를 확정 정책으로 표현하지 않는다.
4. 운송 원가·추가 대기·취소 비용 등은 승인된 운임·비용 근거와 연결한다. 분석상 추정 원가를 회계 정산·실제 지급 완료로 표현하지 않는다.
5. BI / Analytics는 원천 사건·지표 협업만 이 범위에 포함한다. 별도 최종 분석 파일, 독립 분석 서비스의 세부 구현 및 실제 정산 자동화는 이 문서에서 구현 완료로 가정하지 않는다.

**주요 검증 사례**

- 계획 ETA와 실제 도착 시각이 모두 존재하면 두 값을 보존해 ETA 정확도를 계산할 수 있어야 한다.
- 사건이 중복 적재되어도 운송 건수·재배차 횟수·사고 건수가 중복 집계되지 않아야 한다.
- 늦게 도착한 과거 이벤트가 최신 실제 상태를 덮어쓰지 않아야 하며, 승인 정정은 원결과와 정정 사유를 함께 추적할 수 있어야 한다.
- BI 적재 장애가 발생해도 이미 성공한 배정·운송·WMS 원장 반영을 취소하지 않고 분석 적재 단계만 복구해야 한다.

### 1.3.9 관제 시스템 및 BackOffice와의 협업

**TMS 소유 업무**

- 미배차·미출발·지연·미인수·ETA 불명·위치 통신 단절·사고·수량 차이 등 운송 예외를 감지하고, 대상 운송·영향 물량·현재 위치·최근 사건·남은 의무를 제공한다.
- 운영자가 수행할 수 있는 재배차·경로 변경·중단 검토·추가 증빙 요청을 업무 조건과 권한에 맞게 제공하고, 변경 전후 계획과 사유를 보존한다.
- BackOffice가 관리하는 운송 기준정보·계약 요율·운영 정책을 참조하되, 승인되지 않은 정책·비용·사고 처분을 자체 확정하지 않는다.

**관제 시스템 및 BackOffice 소유 업무**

- 관제 시스템은 운영자 권한, 사고·예외 승인, 고객 대응 조율, 운영 개입 이력 및 본사 상신 절차를 소유한다.
- BackOffice는 운송사·계약·요율·운영 정책의 정본과 권한 있는 예외 비용·사고 처리 승인 흐름을 소유한다.
- 실제 외부 운송사 계약/API 연동, 회계 정산 및 실제 입금 자동화는 현재 구현 범위에 포함된 것으로 가정하지 않는다.

**협업 요청·응답 및 실패 처리**

1. TMS는 운송 예외와 함께 현재 상태, 발생 시각, 관련 원요청·배정 버전, 영향 화물, 위치·보관 책임 및 필요한 의사결정 항목을 전달한다.
2. 운영자 개입은 승인된 역할·센터·권역·업무 범위 안에서만 가능하다. 수동 재배차·순서 변경도 실제 인계 여부·현재 배정·용량·시간창·온도·센터 제한을 다시 검증한다.
3. 관제 조회 장애만으로 정상 운행 전체를 중단하지는 않지만, 필수 안전·권한 검증을 수행할 수 없으면 신규 실행을 보류한다.
4. 사고 비용·손실·폐기·반송 등 승인 대상은 TMS의 운송 종료와 별개로 남긴다. 운영자 승인 기록과 실제 물량·원장 대사가 확인되기 전 자동 종결하지 않는다.

### 1.3.10 공통 연계 계약과 사건 처리 규칙

모든 연계에 다음 공통 규칙을 적용한다.

- **요청 정체성:** 각 요청은 원요청 식별자와 버전을 유지한다. 동일 요청의 재전송은 기존 결과 조회·미완료 단계 복구로 처리하고 신규 운송·배정·원장 반영을 중복 생성하지 않는다.
- **사건 정체성:** 실제 출발·인계·전달·회수·수령 사건은 사건 식별자, 실제 발생 시각, 수신 시각, 관련 배송/운송/배정 식별자 및 정정 관계를 유지한다.
- **상태 소유권:** TMS는 계획·배정·ETA·운송 조율을 소유한다. OMS는 주문·취소·환불·주문 이행을, WMS는 재고 원장을, SCM은 공급 결정·이관 승인을, MFC Operations는 현장 준비·수령·검수·인계를, Delivery는 라이더 실제 수행을, Commerce는 고객 노출·알림을, BI / Analytics는 분석 집계를 소유한다.
- **직접 호출과 간접 조율:** 각 시스템이 모두 서로 직접 호출한다고 가정하지 않는다. 직접 조회·검증, 확정 사건 수신, 또는 OMS/SCM 등 승인된 중계 영역을 통한 간접 조율을 연계별로 구분한다.
- **확정과 통지 분리:** 원장 반영·배정 확정 등 업무 성공과 통지·화면 갱신·분석 적재 성공을 별도로 관리한다. 통지 실패는 이미 성공한 업무 결과를 취소하거나 중복 실행할 이유가 아니다.
- **최신성 검증:** 계정 가용성·센터 제한·수령 창·포장 준비·재고 출고 가능 여부 등 시간에 민감한 정보는 배정·픽업·상차·출발 직전에 재검증한다. 오래된 정상 응답이나 조회 불명을 정상으로 간주하지 않는다.
- **부분 결과와 잔여 의무:** 일부 물량·일부 배송·부분 수령·부분 회수만 완료된 경우 남은 수량과 후속 책임을 유지한다. 부분 성공을 전체 성공으로 확장하지 않는다.
- **정정·역순 사건:** 실제 사건이 역순으로 수신되면 실제 발생 시각·증빙·원배정·현재 보관자를 대사한다. 이미 확정된 실제 완료를 단순히 늦게 도착한 이전 단계 이벤트로 되돌리지 않는다. 승인 정정은 원결과와 변경 사유를 보존한다.
- **미설정 값:** 시간창·한도·응답 기한·용량·온도 조건 등이 필수인데 미설정이면 0, 무제한 또는 적합으로 가정하지 않는다. 영향받는 신규 계획·배정·출발을 보류하고 담당자에게 설정을 요청한다.
- **책임 있는 종결:** 종결 시점에는 권한, 최신 버전, 실제 증빙, 수량·품질 차이, 남은 운송·회수 의무, 원장 반영 상태를 확인한다. 운송 종료 버튼 하나로 주문·재고·품질·손실·비용·환불을 일괄 확정하지 않는다.

### 1.3.11 TMS가 반드시 보장해야 하는 운영 원칙

1. 계획 수량·실제 상차 수량·실제 인계/수령 수량을 각각 보존한다.
2. 차량 도착과 하차·인계 완료를 구분한다. 목적지 도착만으로 실물 인수가 완료된 것은 아니다.
3. 운송 중 재고를 직접 판매 가능 재고로 전환하지 않는다.
4. 차량·기사 교체에는 물품 책임의 실제 인계가 필요하다. 배정 정보만 바꾸어 실물 책임이 바뀐 것으로 처리하지 않는다.
5. 부분 운송·부분 배송·부분 인수·부분 회수를 추적한다. 일부 물량이나 배송의 완료로 전체 요청을 완료하지 않는다.
6. 운송 완료와 품질 검수 완료를 구분한다. 이후 확인된 파손·온도 이탈·봉인 훼손은 원운송과 연결한다.
7. 운임·수행료·추가 비용은 근거 사건과 승인 조건을 연결한다. 지연·대기·추가 작업 비용을 임의 확정하거나 실제 지급 완료로 표시하지 않는다.
8. 재시도·중복 메시지·응답 유실이 중복 배차·중복 운송·중복 재고 반영을 만들지 않도록 한다.
9. 배정·ETA·운송 종료는 주문 취소·환불·재고 조정·품질 폐기·고객 약속 변경을 자동으로 확정하지 않는다.
10. 각 연계는 소유 시스템의 사실과 권한을 존중하고, 상대 영역의 기능을 TMS 안에 복제하지 않는다.

### 1.4 핵심 경계·업무 결과의 판단

TMS는 운송 계획·배송 단위·배차·ETA, Delivery는 실제 인수·운송·전달/회수 사실을 책임진다. TMS와 Delivery는 별도 최종 문서와 독립 상태 체계로 관리한다. 배정 결과와 실제 수행 사실의 연결은 유지한다. WMS 재고·OMS 주문·MFC 현장 판정을 운송 상태로 덮어쓰지 않는다.

요청 접수·승인·작업 배정·실제 수행·원장 반영·고객 안내는 각각 다른 결과다. 물리 수량은 센터·SKU·LOT·상태·원실물 단위로, 금액은 원거래·취소 성공/진행·잔액으로 대사한다. 타임아웃·오프라인 기록·GPS 도착·설비 완료 신호만으로 최종 실물/거래를 확정하지 않는다. 권한·최신 버전·실제 증빙·남은 의무를 확인한 뒤 업무를 종료한다.

## 3. DC→PPC 운송 계획·차량·회차



### 3.1 수요 편성·차량·기사

SCM 승인 이관과 WMS의 준비 화물·SKU/LOT·수량·BOX/PLT·중량/부피·온도 조건을 대조한다. 같은 물량을 여러 운송에 중복 배정하지 않는다. 승인 요청은1이관1출발이며 차량 부족을 이유로 같은 요청을 여러 출발로 나누지 않는다. 불가능하면 계획 보류·수량/회차 재승인을 요청한다. 여러 요청을 한 차량에 싣는 것은 각 목적·수량을 구분하고 적재 조건을 통과할 때만 가능하다.

상품뿐 아니라 팔레트·상자·용기 중량과 실측 부피를 포함해 차량/구획 한도를 검사한다. 차량 대수 가용성과 차량1대 적재능력은 별도다. 냉장·냉동 구획·예냉·혼적·적층·압궤·봉인·하차 접근성을 확인하고 안전 한도 초과는 출발을 차단한다. EA를 고정 상수로 팔레트 수나 톤수로 바꾸지 않는다.

기사는 다음 가용 위치/시각·진행 운송·등록 수단의 운반 적합성·근무 조건·계정 제한을 검사한다. 가까워도 수행 중이거나 구획/등록 수단 조건을 못 맞추면 제외한다. 계획되지 못한 요청은 미배정 사유를 유지하고 실패분만 대체 차량/회차로 재검토한다. 성공한 배정을 재계획 때 다시 만들지 않는다.

### 3.3 회차·수령 창·저온 대기의 실행 조건

[채택 설계] DC 작업/출발 회차, PPC 수령/검수 창, 도착 예정, 온도대별 승인 대기 한도를 함께 검사한다. 미설정·조회 불명은 해당 신규 편성/출발을 보류하고 SCM/DC/PPC 담당자에게 보완 요청한다. 이미 운송 중이면 현위치·보관 조건·누적 대기를 확인해 안전 도착/수령을 조율하며 과거 출발을 취소하지 않는다. 저온 분 단위 한도 초과/노출 불명은 품질 사건으로 전달하고 단순 회차 변경으로 이력을 초기화하지 않는다.

라이더 실제 운행과 PPC 준비/인계 시간은 별도 승인 설정이다. 고객 도착 슬롯은 두 조건과 수행 여력이 모두 맞을 때 가능하며00:00~08:00 실제 고객 배송은 허용하지 않는다. 08시/09시 원본 차이를 임의로 하나로 확정하지 않고 해당 센터·일자 승인 설정을 사용한다.

## 4. 간선 출발·운행·도착·차이

출발 전 WMS 승인·검품·실상차, 차량/기사·목적지·봉인·적격 온도, 미취소를 확인한다. 실제 출발 증빙을 WMS와 공유하고 **WMS만 DC 현물 감소·이동 중 전환을 확정**한다. TMS가 두 번째 재고를 차감하지 않는다.

운행 중 위치·통신 최신성·온도 이력·지연 사유·변경 ETA를 기록한다. 도착은 실제 차량 도착, 하차는 실제 화물 인계, 정상 인수는 PPC 검수 합격 결과다. TMS는 하차 수량/화물·시각·담당·사진/봉인 증빙을 제공하고 MFC Operations의 검수 결과를 받는다. 마지막 정차 완료도 미해결 수량·품질 사건을 자동 닫지 않는다.

지연은 계획/고객 약속과 승인된 임계값으로 판단한다. 기한 미설정을0분으로 간주하지 않는다. 후속 정차 ETA를 재계산해 SCM에 공급 유효성 재평가, PPC에 인력/보관 조정, OMS에 고객 약속 영향 검토를 요청한다. 도착 예정 변경으로 과거 약속 위반을 지우지 않는다.

미도착·과도착·오배송·파손·온도 이탈·봉인 훼손은 안전 확보 → 영향 화물 식별 → DC 상차/출발·차량/정차·PPC 재계수 대사 → 책임/처분 승인 순서다. 자동 손실·정상 인수·타 PPC 재배정을 하지 않는다. 출발 후 취소·역이관·강제반송·PPC 간 전환은 초기 미지원이다. 품질상 정상 판매가 불가능하면 보관 책임과 현 위치를 남기고 관제로 상신한다.

수량 차이는3영업일 조사, 추정손실10만원 초과 본사 상신을 지원한다. 종결에는 본사 재고 책임자 또는 운영 본부장 전자 승인과 재고 주체의 대사가 필요하다. TMS 운행 종료와 사고 손실 승인·품질 폐기는 별개다.

[채택 설계] 원출발과 대사한 실제 수령량 전체는 PPC 정상/격리 현물로 귀속하고 이동 중에서 한 번 해소한다. 검수 합격량만 정상, 미판정·부적합량은 격리이며 판매 가용은0이다. 현장 수령 사실은 MFC Operations가 확정하고, 같은 결과의 PPC 정상/격리 재고 반영과 이동 중 해소는 WMS가 수행한다. 격리품 실제 폐기는 WMS가 PPC 격리에서만 차감하고 미수령 잔량은 별도 유지한다. TMS는 인계 화물·실수량·시각·인계자/인수자·위치 증빙만 제공하며 기사 완료가 재고 수령을 대신하지 않는다.

## 5. 간선 화물·수량 대사와 출발 후 사고

운송 요청의 목적지·회차·차량 구획·중량/체적·온도·BOX/PLT구성을 WMS 출고와 비교한다. BOX/PLT는 운송 취급 단위이고 SKU 수량은 하위 구성으로 대사한다. 다른 PPC 화물 상차·온도 부적합·하중/수령 창 미확인은 출발을 보류한다. 고객배송10kg 규칙을 간선BOX 최대중량으로 대체하지 않는다.

실제 출발 증빙은 WMS의 DC차감/이동중 전환을 뒷받침하지만 TMS가 독립 재고를 변경하지 않는다. 도착·하차·MFC 실수령·WMS PPC 반영·판매 준비를 분리한다. 출발48·수령46이면 이동중2를 조사하며 실제 격리2와 미수령2를 혼동하지 않는다. ETA지연은 PPC수령 창·품질/기한·SCM보호기간을 재검증하고 기존 고객 약속 변경은 OMS 판단으로 넘긴다.

한 요청 한 출발과 출발 후 목적지 변경·자동 역이관/실제DC반송 초기 제외를 유지한다. 신규 자료의 경로 전환·역방향TRF는 향후 제안으로 보존하고 원운송 완료 버튼으로 실행하지 않는다. 사고 실물은 현재 위치/보관 책임을 기록하고 목적 PPC 안전 수령과 품질/차이 해결을 조율한다.

[채택 설계] DC 실제 출발 이후에는 원이관 취소·타PPC 경로 전환·자동 역이관/강제반송을 지원하지 않는다. 목적 PPC에서 실제 물량을 확인해 합격분만 정상 인수하고, 의심/부적합품은 온도를 유지한 별도 위치에 안전 보류한다. 정보 오류나 의심이 해소된 적격품만 재검수 후 인수할 수 있으며, 부적합 확정품은 본사 품질 책임자의 승인과 실제 폐기 증빙으로 처리한다. 실제 DC 반송은 초기 구현 범위에서 제외한다.

원출발·인수 실적을 지우거나 반송 의사만으로 DC 재고를 늘리지 않는다. 미해결 수량과 보관 책임·현재 위치를 유지하고, 폐기는 같은 물량을 소유한 원장에 한 번만 반영한다. 격리품 처분과 미수령 잔량은 별도 대사하며 동일 손실을 두 번 차감하지 않는다.

## 6. 고객 배송 생성·분할·배차



### 6.1 요청 자격과 분할

OMS의 확정/미취소 배송과 MFC Operations의 포장 준비예상·봉투·중량·부피·온도 요구를 받는다. 패킹 중에도 예상 소요시간이 있으면 배차를 시작할 수 있지만 실제 픽업은 검품 완료 후다. 준비예상 변경은 기사 ETA와 대기를 재평가한다.

`[확정 정책]` 상품중량 **10,000g 초과**는 같은 주문 안에 여러 배송을 만들고 각 배송 상품중량을10,000g 이하로 배분한다. 주문·PG 결제·봉투값은1회이며 분할 추가 배달팁은 없다. 정확히10,000g은 이 기준에 의한 분할 대상이 아니다. 수단별 용량·부피·봉투·보냉 조건은 별도로 더 엄격하게 적용한다. 배송별 대상 포장·수량·라이더를 구분하며 원주문과 연결한다.

단일 상품10kg 초과, 포장재 중량 포함, 온도 혼재 운송 기준은 팀 확인 전 무단 분할/과적하지 않는다. 부피 때문에 추가 라이더가 필요한 경우도 독립 배송 구성과 수량 합계를 검증한다. 같은 포장을 여러 배송에 중복 배정하지 않는다.

### 6.2 후보·제안·수락

계정 정상·운행/신규배차ON·권역·위치 최신성·수단/용량·진행 배송·시간창을 검사한 후보만 제안한다. 도로 이동시간은 기사→PPC→고객과 기존 수행 전체를 평가한다. 최인접 기사와 전체 경로시간 최소 기사는 다를 수 있다. 경로 추천/AI 결과는 제약을 다시 검증하고 불가능한 제안은 미배정으로 남긴다. 모델 도입·성능이 검증된 것으로 가정하지 않는다.

제안에는 픽업지·고객 전달권역·배송 방식·예상 준비/운행시간·봉투/중량·수행료·특별조건·응답기한을 보여준다. 민감한 상세주소는 수행 단계에 필요한 범위만 공개한다. 거절·미응답·알림 실패·만료를 각각 기록한다.

동시 수락은 같은 배송에 유효 기사1명만 확정한다. 늦은 수락은 이미 배정/만료/주문 취소/자격 또는 용량 부족을 구분한다. 재전송은 기존 수락 결과를 반환한다. 배정 취소는 라이더의 수행 권한 해제이며 고객 주문 취소와 다르다.

## 7. Delivery 가용성 수신과 배정 검증

후보 정보는 Delivery의 프로젝트 계정 정상 여부·운행/신규배차 허용·등록 수단·활동권역·위치 최신성·현재 수행·제한 상태를 사용한다. TMS는 이 정보를 임의로 정상화하지 않고 배정 직전에 다시 검증한다. 실제 면허·보험·계좌 소유 검증은 프로젝트 범위에서 제외하며 입력 정보를 실제 검증 완료로 표시하지 않는다.

일반 목록·추천 제안·수동 배차도 같은 단일 유효 배정과 수단/시간/용량 검증을 적용한다. 한 건씩 수행 설정은 현재 배송 종료 전 새 배정을 제한한다. 신규배차OFF·알림OFF·앱 통신 단절은 서로 다르며 진행 배송을 자동 취소하지 않는다. 상세 계정 변경과 단말·운행 조작은 Delivery가 처리하고 TMS는 현재 배정 가능 여부를 소비한다.

## 8. 경로·ETA·약속 시간의 관리

방문 순서·ETA는 기사→PPC와 PPC→고객뿐 아니라 기존 수행의 남은 전체 구간·정차/대기·준비시간을 포함해 계산한다. 최인접 기사와 전체 운행시간 최소 기사는 다를 수 있다. 추천/AI 계산은 실행 가능한 후보안이며 계정/용량/시간창/한집 조건 검증을 통과하고 수락이 확정돼야 배정이 된다. 모델·외부 지도 API가 구현·성능 검증됐다고 가정하지 않는다.

Delivery의 현재 위치는 생성시각·수신시각·정확도·통신 상태와 함께 사용한다. 위치 불명/오래된 좌표는 현재 위치로 추정하지 않고 영향 ETA를 확인 중으로 표시한다. 준비 지연·픽업 대기·교통·사고·수행 순서 변경 때 후속 구간까지 재계산하며 계획 시각·최신 예상·실제시각을 보존한다.

예측 ETA가 바뀌었다고 OMS의 확정 예약 약속을 조용히 변경하지 않는다. 변경 영향을 OMS/Commerce와 PPC에 제공하고 고객 안내는 유효 최신 결과로 수행한다. 고객에게는 본인 배송까지의 허용 ETA/진행만 제공하며 다른 고객 주소·기사 전체 경로를 공개하지 않는다. ETA 서비스 실패 시점·영향 배송·다음 조회/담당을 남기고 GPS만으로 완료를 확정하지 않는다.

## 9. 실제 수행 결과 수신·OMS/WMS 연계

MFC Operations는 유효 포장·준비 완료·출고 중지·최종 현장 인계 사실을, Delivery는 라이더의 실제 수령·이동·전달/회수 사실을 확정한다. TMS는 원배송·포장·기사·현재 배정 버전과 결과를 대사하고 경로·ETA·남은 배정을 갱신한다. 배정 성공·GPS 도착·픽업 예정만으로 실수령이나 WMS 차감을 만들지 않는다.

수행 결과가 먼저 도착하거나 응답이 유실되면 원배정과 실제 인계/전달 사건을 조회한다. 같은 사건의 재전송은 진행 단계와 실적을 중복 생성하지 않는다. 실제 완료 뒤 늦은 도착 이벤트로 진행 상태를 역행시키지 않고, 승인 정정은 원결과와 변경 사유를 보존한다. 실제 전달 증빙 없는 시간 경과만으로 완료를 합성하지 않는다.

Delivery가 배송별 완료·실패·미전달·현재 보관자를 반환하면 TMS는 OMS에 해당 결과와 후속 운송 가능성을 전달한다. 고객 주문 전체 이행·취소·환불은 OMS, PPC 현물/예약은 WMS가 확정한다. 수행료 확정·모의 지급은 Delivery가 관리하며 TMS는 제안/수락 당시 조건과 거리·배정·지연·취소 이력만 근거로 제공한다. 재고·PG·수행료를 운송 완료와 동시에 자동 확정하지 않는다.

## 10. 취소·중단·재배차와 예약 변경

### 10.1 픽업 전 배정 해제와 경합

라이더의 배정 취소·노쇼·지속 지연 또는 OMS 취소 요청이 있으면 현재 유효 배정과 MFC의 포장별 인계 상태를 조회한다. **미인계 확인**이면 이전 기사 권한을 해제하고 같은 배송의 후속 배차를 진행한다. 고객 주문 취소는 OMS의 별도 판단이므로 배정 해제만으로 환불·예약 해제를 확정하지 않는다.

출고 중지가 먼저 확정되면 해당 포장에 신규 실행 지시를 내리지 않는다. 인계 진행/사실 불명이면 배정만 해제해 다른 기사에게 같은 포장을 넘기지 않고 MFC 최종 판정·Delivery 실수령을 확인한다. 실수령이면 현재 보관자와 안전 회수/승인 재인계가 확인될 때까지 책임을 유지한다. 취소 시각·지시 발송 성공만으로 과거 실물 인계를 없애지 않는다.

### 10.2 픽업 후 사고와 재배차

사고·고장·이탈·파손·오배송·위험 상황은 Delivery가 현재 위치·물품·보관 조건·수행 가능성을 보고한다. TMS는 운영 승인과 실물 인계 가능 지점을 확인해 후속 회수/대체 기사 계획을 만든다. 원기사 임무 종료, 물품의 실제 재인계, 새 기사의 배정은 서로 다른 결과이며 임의 양도를 허용하지 않는다.

새 경로/기사/방문 순서는 전체 기존 수행·시간창·한집 제약·용량·온도·PPC/고객 준비를 다시 검증한다. 재계산 불가 또는 지도 서비스 장애면 마지막 계획을 무조건 유효로 쓰지 않고 영향 구간의 ETA 확인 대기와 담당 대응을 유지한다. 권역 변경·추가 거리/보상·귀책은 별도 승인 대상으로 남긴다.

### 10.3 예약 변경과 주문 조건

결제 후 고객 주소·연락처·요청 사항은 변경하지 않는다. 예약 시간만 OMS가 상품준비 전 새 슬롯·재고·기한·현장 여력을 검증해 확정한 결과를 반영한다. 미수락 제안과 배정 계획의 구버전을 종료/갱신하고 늦은 수락을 차단한다. 새 계획이 실패하면 OMS가 확정한 원주문과 고객 약속을 임의로 다른 시간/주소로 바꾸지 않는다.

## 11. 고객 회수·교환·재배송의 운송 계획

OMS가 승인한 원주문·원배송·대상 품목/수량·고정 회수주소·목적 PPC·사유를 받아 독립 회수 임무를 계획한다. 원기사 또는 새 후보를 검증하고 회수 준비·수용 창·수단/온도·기존 운행과 충돌 없는 배정을 확정한다. Delivery에 실행을 요청하고 고객 수거·PPC 반납·MFC 수령·검수 결과를 각각 수신한다. 실제 수거/반납 방법과 증빙 절차는 Delivery/MFC가 주관한다.

부분 수거·미반납·품질 보류는 남은 수량과 책임자를 유지하고 작업 요청 성공으로 회수 전체를 끝내지 않는다. 재배송/교환 배송은 원의무와 연결한 별도 배송·포장·배정으로 관리한다. 고객 환불이나 귀책 판단은 OMS와 승인 담당자, 재고 복구/폐기는 WMS가 확정하며 TMS가 재고를 직접 가산하지 않는다.

고객 교환·반품 접수 자격은 일반 수령7일·신선24시간, 하자/오배송/광고 상이 교환은3개월 또는 인지30일 조건을 OMS가 판단한다. 단순 변심 교환 왕복 합계9,000원·상품/배달 문제 구매자 무상은 OMS 승인 비용으로 받고 분할 회수·새 기사 배정마다 고객에게 중복 청구하지 않는다. 상세 라이더 보수/회수료·고객 일반 반품비가 자동 승인된 것으로 가정하지 않는다.

## 12. 센터 운영 제한과 안전 실행 조건

[채택 설계] PPC 운영 제한 정본은 MFC Operations, DC는 WMS다. TMS는 차량·라이더 가용성만 주관하고 센터 제한을 자체 해제하지 않는다. 배차·픽업/상차·출발 직전에 최신 업무별 제한을 검증한다. 접수 중지만으로 수행 배송을 취소하지 않고 안전 인계 중지는 영향 신규 픽업을 보류해 위치·보관 책임·OMS 영향 주문을 전달한다. 조회 불명/오래된 정상 응답으로 수행을 시작하지 않는다. 운송 중 안전 확보와 사고 조사·원수행 결과 수신·후속 계획 의무는 유지한다.

## 13. 권한·연계 실패·중복·복구와 종결

운영자는 허용 센터·권역·업무의 계획/배정만 변경한다. 수동 배차·재배차·순서 변경도 원요청·최신 배정·실물 인계 여부·승인·수단/시간/제한 조건을 검사한다. 고객 주문/재고/실제 전달 결과를 계획 수정으로 덮어쓰지 않는다.

접수·제안·수락·배정 해제·실행 지시는 같은 원요청/원시도와 결과를 연결한다. 응답 유실은 기존 결과 조회 후 미완료 단계만 재전달한다. 다른 주문 내용으로 기존 요청을 덮어쓰거나 수락 재시도로 새 배정을 중복 생성하지 않는다. 알림 실패와 배정 실패를 구분해 실제 성공한 배정을 취소/재생성하지 않는다.

Delivery 오프라인 수행 또는 역순 사건은 원배정·실제 시각·현장 인계·현재 보관자를 대사해 계획에 반영한다. 배정상 공백이 있어도 이미 실수령한 물품을 없는 것으로 보고 재픽업시키지 않는다. TMS 복구 후 미해결 요청·배정·실물/결과 불명·회수·사건을 주관 시스템과 대사한다. 관제 조회 장애만으로 정상 운행 전체를 중단하지 않되 필수 안전/권한 검증 불가는 보류한다.

## 부록 A. 기준 문서의 업무 범주와 용어 정합성

이 부록은 TMS-basic-v2.md에서 제시한 업무 범주를 상세 비즈니스 로직 문서의 규칙과 연결하기 위한 기준이다. 본문에 명시된 현재 범위·확정 정책·채택 설계·팀 확인 필요 사항을 변경하거나 대체하지 않는다.

### A.1 운송 기준정보

- 출발·도착 거점, 운송 구간, 차량 종류, 적재 중량·부피, 냉장·냉동 조건, 상하차 가능 시간, 운송 수단 적합성, 서비스 가능 권역 및 운영시간을 계획 검증의 입력으로 사용한다.
- 운송사·기사·차량 관련 정보는 현재 구현 범위에서 실제 자격 검증 완료를 의미하지 않는다. 라이더 계정·앱·운행 상태와 상세 자격·단말 처리는 Delivery의 책임이다.
- 필수 기준정보가 없으면 영향을 받는 신규 계획·배정·출발을 보류한다. 미설정 값을 0, 무제한 또는 적합으로 간주하지 않는다.

### A.2 운송 요청 접수

- SCM의 승인 이관과 OMS의 유효 고객 배송 요청을 수신한다. 요청별 출발지·목적지·물품·수량·필요 도착시간·버전·취소 상태를 검증한다.
- 동일 원요청 재전송은 기존 결과를 반환하고, 요청 내용이 달라졌다면 기존 요청을 덮어쓰지 않고 승인된 변경 버전 또는 새 요청으로 처리한다.
- 외부 공급업체에서 DC로 들어오는 실제 입고·검수 및 구매발주는 초기 구현 범위에서 제외한다. 승인된 DC 초기 보유부터 운영하며, DC→PPC 보충과 고객 주문 이행을 포함한다.

### A.3 운송·적재 계획

- 요청을 배송·운송 단위로 구성하고 직송·다중 경유 여부, 방문 순서, 출발·도착 예정시간, 차량 수요, 중량·부피·온도·혼적·하차 접근성 등을 검증한다.
- 고객 배송의 상품중량 10,000g 초과 분할 정책과 간선의 승인 이관 1건당 1회 출발 정책은 서로 다른 규칙이다. 고객 배송 규칙을 간선 BOX/PLT의 최대 중량으로 대체하지 않는다.
- 차량·구획 한도를 초과하거나 수령 창·필수 제약을 검증할 수 없으면 출발을 보류한다. 차량 부족을 이유로 승인 이관을 임의로 여러 출발로 나누지 않는다.

### A.4 배차·운송사 또는 라이더 할당

- 고객 배송에서는 Delivery가 제공하는 계정 정상 여부, 운행·신규 배차 허용, 등록 수단, 권역, 위치 최신성, 진행 배송 및 제한 상태를 사용한다. TMS는 배정 직전에 다시 검증한다.
- 간선 차량·기사 편성은 차량·기사 가용성, 적재 능력, 등록 수단 적합성, 시간창, 온도 조건 및 운행 충돌을 확인한다.
- 제안·수락·거절·만료·배정 확정·배정 해제·재배차를 구분한다. 같은 배송에는 유효 기사 1명만 확정하며, 동시 수락과 늦은 수락은 원자적으로 대사한다.
- 외부 운송사 계약/API 연동은 이미 구현된 것으로 간주하지 않는다.

### A.5 출발지 준비·상차 및 인계

- 차량 도착, 출고 준비 완료, 실제 상차, 실제 출발, 물품 인수 증빙은 서로 다른 사실이다.
- 간선은 WMS의 출고 승인과 실상차 정보를 확인하고, 실제 출발 증빙을 WMS에 전달한다. 재고 차감과 이동 중 전환은 WMS가 확정한다.
- 고객 배송은 MFC Operations의 포장·검품·최종 인계와 Delivery의 라이더 실제 인수를 구분한다. 배정 성공이나 준비 예상만으로 픽업 완료를 만들지 않는다.
- 누락·파손·초과 상차·봉인·온도 이상은 영향 화물과 증빙을 연결하고 안전·품질·재고 책임 절차로 전달한다.

### A.6 운행 추적·도착·하차·인계

- 출발·이동·경유·도착 상태, 위치 최신성, ETA, 운행 지연, 경로 이탈 및 통신 단절을 추적한다.
- 실제 도착, 실제 하차, 실제 인계, 현장 검수, 원장 반영을 구분한다. GPS 도착만으로 완료를 확정하지 않는다.
- 운송 중 품질·사고는 온도 이탈, 차량 고장, 사고, 분실·파손, 긴급 정차·차량 교체 등으로 분류하고 현재 위치·보관 책임·영향 물량·조치·승인 이력을 유지한다.
- 간선 수령 결과는 MFC Operations가 확정하고 WMS가 정상·격리·이동 중 잔량을 원장에 반영한다. 고객 전달·회수 결과는 Delivery가 실제 수행 사실을 확정하고 OMS가 주문 이행·취소·환불을 판단한다.

### A.7 변경·취소·회수·반송

- 배차 전·후·상차 후 변경은 실제 인계 여부와 적용 가능한 정책에 따라 판단한다. 운송 요청 취소와 배정 해제는 주문 취소와 다르다.
- 픽업 전 미인계가 확인된 경우 배정 해제와 후속 배차를 검토할 수 있다. 인계 진행 중·불명 또는 실수령 상태에서는 현재 보관자와 안전한 실제 재인계를 확인하기 전 새 수행을 시작하지 않는다.
- OMS가 승인한 고객 회수·교환·재배송은 원주문·원배송·대상 품목·수량·고정 회수주소·목적 PPC·사유와 연결한 별도 운송 의무로 관리한다. 부분 회수·미반납·품질 보류가 남으면 의무를 유지한다.
- DC 출발 후 목적지 변경·타 PPC 전환·자동 역이관·강제반송·실제 DC 반송은 초기 구현 범위에서 제외한다. 향후 제안과 현재 실행 가능 기능을 혼동하지 않는다.

### A.8 운임·실적·관제·복구

- TMS는 배정·재배정·거리·시간·지연·취소 등 비용 산출의 기초 사실과 증빙을 제공한다. 최종 수행료는 Delivery, 계약·요율 및 예외 비용 승인은 BackOffice/권한 있는 담당자가 소유한다. 실제 회계 정산·입금 자동화는 초기 범위에 포함되지 않는다.
- 미배차·미출발·지연·미인수·중복/역순 이벤트·외부 서비스 장애를 탐지하고, 성공한 원장 반영과 실패한 통지·조회·분석 적재를 분리한다.
- 장애 복구는 원요청·원사건·현재 배정 버전·실제 인계·현재 보관자·남은 의무를 주관 시스템과 대사한 뒤 미완료 단계만 재시도한다.
- BI / Analytics에는 지표 산출용 원천 사건과 근거를 제공한다. 분석 집계는 운송·주문·재고 상태의 정본이 아니며, 분석 적재 실패로 이미 성공한 업무를 되돌리지 않는다.

### A.9 범위·정책의 우선 적용

- 이 문서에서 `[확정 정책]`으로 표시한 사항은 확정 정책으로 취급한다.
- `[채택 설계]`는 현재 문서에서 선택한 구현 방향이며, 다른 영역의 정본·승인 권한을 대체하지 않는다.
- `[설계안]`은 승인 전 확정 정책으로 간주하지 않는다.
- `[팀 확인 필요]` 또는 미결정·운영 승인 대기 항목은 임의로 값을 채우지 않는다. 필수 입력이 없는 경우 영향을 받는 신규 업무를 보류하고 담당자에게 확인한다.
- 본 문서는 상세 업무 규칙과 협업 경계를 정의한다. 본문에 제외로 명시한 외부 입고, 외부 운송사/API 연동, 실제 자격 검증, 실제 송금, 초기 제외된 역이관·반송 기능을 묵시적으로 포함시키지 않는다.
