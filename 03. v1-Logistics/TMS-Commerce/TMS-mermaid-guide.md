# TMS 업무 흐름 Mermaid 가이드

## 1. 문서 목적

이 문서는 `TMS-final.md`의 업무 규칙을 빠르게 이해할 수 있도록 Mermaid 다이어그램으로 표현한 보조 문서입니다.

- 원문 업무 규칙을 다시 복사하지 않고, 주요 흐름과 시스템 간 책임 관계를 그림으로 정리합니다.
- 상세한 조건, 예외, 수용 기준 및 미결정 사항은 `TMS-final.md`를 기준으로 확인합니다.
- 다이어그램은 업무 이해를 돕는 표현이며, 원문에 확정되지 않은 정책을 새로 확정하지 않습니다.

## 2. TMS 전체 업무 흐름

주문·출고 준비 정보부터 배차, 배송, 완료 결과까지 이어지는 대표 흐름입니다. 실제 실행 순서와 선행 조건은 연계 시스템 및 업무 상황에 따라 달라질 수 있습니다.

```mermaid
flowchart TD
    A["주문 및 배송 요청 정보"] --> B["배송 가능 정보 확인"]
    B --> C["운송 계획 수립"]
    C --> D["운송 건 구성 및 배차"]
    D --> E["운송 실행"]
    E --> F["위치·상태·ETA 갱신"]
    F --> G{"배송 결과"}
    G -->|정상 완료| H["배송 완료 처리"]
    G -->|실패·지연| I["예외 처리 및 재조정"]
    G -->|취소·반송 필요| J["취소·회수·반송 흐름"]
    I --> F
    J --> K["결과 및 이력 기록"]
    H --> K
    K --> L["성과·운영 데이터 제공"]
```

## 3. TMS와 주변 시스템의 책임 경계

이 그림은 TMS가 모든 업무를 직접 소유하는 것이 아니라, 각 시스템의 책임 정보를 받아 운송을 계획·조정하고 결과를 전달하는 구조를 나타냅니다.

```mermaid
flowchart LR
    COM["Commerce<br/>주문·고객 요청"] --> TMS["TMS<br/>운송 계획·배차·배송 가시성·예외 조정"]
    OMS["OMS<br/>주문 이행 상태"] <--> TMS
    WMS["WMS<br/>창고 출고·인계 준비"] <--> TMS
    SCM["SCM / Replenishment<br/>재고 보충·이동 수요"] <--> TMS
    MFC["MFC Operations<br/>마이크로 풀필먼트 운영"] <--> TMS
    DEL["Delivery / 운송 실행 주체<br/>운행·배송 결과"] <--> TMS
    TMS --> BI["BI / Analytics<br/>운송 실적·지표"]
    CTRL["Control System / BackOffice<br/>운영 관리·설정·감사"] <--> TMS
```

**읽는 방법**
- TMS는 운송 계획, 배차, 운송 진행 상태 및 예외 조정을 중심으로 동작합니다.
- 주문·재고·창고·MFC의 원천 업무 상태를 TMS가 임의로 대체하지 않습니다.
- 실제 연계 방향, 이벤트 및 필수 필드는 `TMS-final.md`의 통합 계약과 각 영역별 규칙을 따릅니다.

## 4. 계획부터 배차까지의 의사결정 흐름

```mermaid
flowchart TD
    A["운송 요청 수신"] --> B{"요청 데이터와 필수 조건이 유효한가?"}
    B -->|아니오| C["오류·누락 정보 처리"]
    C --> D["수정 요청 또는 재처리 대기"]
    B -->|예| E["운송 제약·가용성 확인"]
    E --> F{"운송 계획 수립 가능?"}
    F -->|아니오| G["계획 불가 사유 기록 및 조정"]
    G --> E
    F -->|예| H["운송 건 구성"]
    H --> I["배차 대상·자원 결정"]
    I --> J{"배차 확정 가능한가?"}
    J -->|아니오| K["재배차·대안 검토"]
    K --> I
    J -->|예| L["배차 확정 및 관련 시스템 통지"]
    L --> M["운송 실행 단계로 전환"]
```

> 이 다이어그램의 판단 지점은 개념적 단계입니다. 구체적인 검증 규칙, 자원 선정 방식, 재시도 횟수 또는 타임아웃이 원문에서 확정되지 않았다면 구현 정책으로 간주하지 않습니다.

## 5. 운송 상태와 예외 처리의 개념 흐름

```mermaid
stateDiagram-v2
    [*] --> 요청접수
    요청접수 --> 계획수립: 요청 검증 통과
    요청접수 --> 예외검토: 데이터 오류·조건 미충족
    예외검토 --> 요청접수: 수정 후 재처리
    예외검토 --> 취소처리: 취소 결정
    계획수립 --> 배차대기: 계획 구성
    배차대기 --> 배차확정: 배차 확정
    배차대기 --> 예외검토: 자원 부족·배차 실패
    배차확정 --> 운송중: 운송 시작
    배차확정 --> 취소처리: 실행 전 취소
    운송중 --> 배송완료: 배송 성공
    운송중 --> 예외검토: 지연·배송 실패·운행 문제
    예외검토 --> 운송중: 조정 후 운송 재개
    예외검토 --> 회수반송: 회수·반송 처리 필요
    회수반송 --> 종료: 회수·반송 결과 기록
    배송완료 --> 종료
    취소처리 --> 종료
    종료 --> [*]
```

**주의:** 위 상태도는 이해를 위한 개념 모델입니다. 실제 상태 코드, 허용 전이, 취소 가능 시점 및 반송 조건은 원문에서 정의한 규칙을 우선합니다.

## 6. 배송 진행 정보와 ETA 갱신

```mermaid
sequenceDiagram
    participant D as Delivery / 운송 실행 주체
    participant T as TMS
    participant O as OMS / 주문 상태
    participant C as Commerce / 고객 접점
    participant B as BI / Analytics

    D->>T: 운송 시작·위치·배송 이벤트
    T->>T: 운송 상태 및 ETA 반영
    T-->>O: 필요한 운송 상태 전달
    T-->>C: 제공 대상 배송 상태·ETA 전달
    T-->>B: 운송 이벤트·성과 데이터 제공
    D->>T: 배송 완료 또는 실패 결과
    T->>T: 결과 검증 및 이력 기록
    T-->>O: 최종 운송 결과 전달
    T-->>C: 고객 접점에 필요한 결과 전달
    T-->>B: 최종 결과 및 지표 데이터 제공
```

이 흐름은 논리적인 연계 예시입니다. 모든 이벤트가 모든 시스템으로 직접 전달된다는 의미는 아니며, 실제 구독자·전달 조건은 인터페이스 정의를 따릅니다.

## 7. 취소·배송 실패·반송의 분기

```mermaid
    B -->|실행 전 취소 가능| C["취소 규칙 검증"]
    C --> D["취소 상태 및 연계 시스템 반영"]
    B -->|운송 중 지연·실패| E["실패 사유와 최신 상태 기록"]
    E --> F{"운송 재개 또는 재배차 가능?"}
    F -->|가능| G["운송 계획·배차 조정"]
    G --> H["운송 재개"]

    B -->|완료 후 문제| K["완료 이력과 사후 처리 규칙 확인"]

    H --> L
    J --> L
    K --> L
```

## 8. 시스템 연계 이벤트의 공통 처리 흐름

```mermaid
flowchart TD
    A["외부 시스템 이벤트 수신"] --> B["필수 식별자·필드 확인"]
    B --> C{"유효한 이벤트인가?"}
    C -->|아니오| D["오류 기록 및 정의된 오류 경로 처리"]
    C -->|예| E["중복·순서·현재 상태 검토"]
    E --> F{"정상적으로 반영 가능한가?"}
    F -->|예| G["TMS 상태·업무 데이터 반영"]
    F -->|아니오| H["충돌·재처리·수동 검토 경로"]
    G --> I["처리 결과 및 감사 이력 기록"]
    D --> I
    H --> I
    I --> J["필요한 후속 이벤트·알림 발행"]
```

**설계 시 확인할 항목**
- 이벤트 식별자와 업무 식별자
- 중복 수신 시 멱등 처리 기준
- 이벤트 순서가 뒤바뀌거나 늦게 도착한 경우의 처리
- 실패 재시도와 수동 복구의 책임 주체
- 상태 변경 이력 및 감사 기록
- 오류 응답, 재처리 가능 여부 및 모니터링

위 항목은 연계 설계 검토 목록입니다. 구체 값과 정책은 `TMS-final.md`에 명시된 내용 또는 별도 합의된 인터페이스 명세에서 확인해야 합니다.

## 9. 운영 지표와 데이터 흐름

```mermaid
flowchart LR
    A["계획·배차 데이터"] --> D["TMS 운송 이력"]
    B["위치·ETA·배송 이벤트"] --> D
    C["취소·실패·반송 데이터"] --> D
    D --> E["운영 모니터링"]
    D --> F["운송 성과 분석"]
    D --> G["예외 원인 분석"]
    E --> H["운영 조치·계획 조정"]
    F --> I["성과 개선 검토"]
    G --> H
```

분석 지표의 정확한 산식, 집계 주기, 목표치 및 데이터 보존 기준은 이 그림에서 정의하지 않습니다. 해당 기준이 필요한 경우 원문 및 별도 BI 정의를 확인합니다.

## 11. 정책 확정 상태에 대한 원칙

- 이 문서는 시각화 보조 자료이며 `TMS-final.md`를 대체하지 않습니다.
- 원문에서 미결정으로 남긴 정책은 이 문서에서도 확정된 것으로 취급하지 않습니다.
- 다이어그램의 화살표는 개념적 업무 흐름 또는 논리적 연계를 나타내며, 그 자체로 API, 메시지 토픽, 동기/비동기 방식이나 구현 완료를 의미하지 않습니다.
- 구현·테스트 시에는 원문의 업무 규칙, 수용 기준, 미결정 사항 및 승인된 인터페이스 명세를 함께 확인합니다.
